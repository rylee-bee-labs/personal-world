## Your DESIGN.md

# Worlds vNext — v7989: The Service Cabinet

**MOCKUP** · Design decisions for a warm, working shell that gives each service a clear owner and each shared fact a clear source.

## 1. Metaphor in one line, and the main gesture.
Worlds is a small, welcoming service cabinet: choose a named service to see its own app beside the facts Worlds shares. The main gesture is **open a service and follow one fact across its views**. A tiny inline-SVG cabinet-label illustration adds warmth; no status depends on it.

## 2. Integration model: how a service plugs in, where it lives in the shell, how its facts flow.
Start with exactly Media Shelf (`media-shelf`, `healthy`) and Front Door (`front-door`, `needs_attention`). The visible **#add-service** button starts Notes Sync (`notes-sync`, `unavailable`) through Discover → Credential reference (reference only; never a secret) → Safe test → Preview → Choose facts to publish → Publish. Its preview retains `sync.provider-reachable` (`unavailable`), `sync.local-pending` (3 notes, `live`), and `sync.last-synced` (`stale`); provider trouble does not erase local notes. Service apps own actions and data; Worlds displays published facts from one shared store. The selected service has a visible **#disconnect** on the first screen; confirm by service name with a button labelled **Disconnect**. Disconnect removes its app and current service view, leaves the shell and remaining services usable, and states plainly what disappeared; history retention is UNKNOWN. Include the only other fixture service, Nightly Backup, only if needed for an error-state illustration; never invent services or readings.

## 3. Navigation between Worlds and a service (phone and desktop).
Persistent destinations are Home, Connect, Memory, Settings. Desktop uses a compact top bar and a two-column working area: fixed-order service list, then selected service detail. Home summarizes the same states; Connect holds lifecycle and connected services; Memory shows shared facts; Settings groups appearance/comfort and the live feed. On mobile, a four-item bottom navigation remains reachable, with one-column screens and an explicit Back link from service detail to the service list. Source order is navigation, main, then complementary fact details; focus follows it. At 390px, no sideways scroll, safe-area padding, and every target is at least 44px. At 1440px, keep the register and service detail side by side with readable measure, not stretched cards.

## 4. The embedded-app frame (sandbox, fallback, what the shell keeps around it).
The selected owner app sits in a clearly titled, softly rounded inset frame, with its service state and owner named at the frame edge. Keep the owner fallback visible: Media Shelf — “Open Media app” (`app://media`); Front Door — “Open Home app” (`app://home`); Notes Sync — “Open Memory app” (`app://memory`). Keep Worlds navigation, service status, and shared fact card outside the frame. If embedding fails, say what failed and retain the owner link and facts. Worlds sends no credential value into the frame. Actual browser isolation, sandbox flags, and app messaging are UNKNOWN; approvals hand off to Project Home, other actions to their owning app.

## 5. The agent/human shared-facts model (source, freshness, who sees, who acts).
Home, the selected service’s fact card, and Memory’s Agent facts view subscribe to the same fixture-keyed state. Each fact shows value, source, checked/observed time, freshness word, Agent visibility, Human visibility, and who may act. Keep permissions separate: `frontdoor.back-door` is agent `read`, human `act`, with its fixture reason; `frontdoor.unlocked-for` is `read` for both; `frontdoor.guest-code-used` is human `read`, agent `none`, rendered as a named disabled control with the exact fixture reason. **#simulate-change** applies only the fixture’s `lock-back-door` example: `frontdoor.back-door` becomes “locked,” Front Door becomes `healthy`, Home attention count becomes 0, and Agent facts updates in the same state commit. This is a mock review/handoff, not a Worlds decision or real door action.

## 6. States: empty/first run (zero services, zero providers), quiet, needs-you, stale, unknown, disconnected.
First run with zero services offers “Connect a service” and explains that local Memory works without a provider; zero providers means no readings. Quiet uses Media Shelf’s exact healthy summary. Needs-you uses Front Door’s fixture reason, with a calm owning-app handoff. Notes Sync keeps provider unavailable, local pending live, and last sync stale as distinct facts. Unknown is stated in words with its fixture reason, never treated as healthy. Disconnected names the removed service and what remains. Test failure explains the failed check and recovery, retaining the credential reference; long copy and empty preview still have recovery controls. Live freshness ages from fixture timestamps; the feed is ON by default, occasionally marks a service stale, and updates Home, service and facts without reload. **#live-toggle** visibly pauses/resumes data updates; reduced motion suppresses movement, not data updates. A connected confirmation is one gentle, one-shot label transition plus “Connected — your chosen facts are now in Worlds”; static text carries the state. No shimmer or looping motion.

## 7. Borrowed from Homarr / Dashy / HA cards / MCP ext-apps, and what is deliberately different.
Borrow Homarr’s one integration feeding UI and assistant, Dashy’s in-place app opening, Home Assistant cards’ shared subscriptions, and MCP ext-apps’ contained UI boundary. Worlds keeps an explicit owner and permission/freshness context attached to each fact, instead of turning providers into a dashboard catalog or letting an embedded app replace the shell. The cabinet is a fixed, labeled register—not a map, route diagram, or unfolding place.

## 8. Your OpenDesign starting point (skill + design system) and how you used it; which guide rules you applied.
Starting point: `skill-emil-design-eng.md` and `ds-airbnb.md`. Use Airbnb’s near-black text, restrained coral for the primary Connect action, hairline separators, rounded app frame, and 8px-based spacing; use system sans fallbacks, not a remote/proprietary font. Keep the source system’s clean hospitality but replace its bright white canvas with a warm, low-glare neutral; coral is an accent, never small text unless contrast passes. Apply Emil’s purposeful, brief, interruptible feedback; the craft rulebooks’ anti-slop constraints, limited accent, readable type, explicit loading/empty/error/edge states, native controls, contrast/focus/touch requirements, and reduced-motion rules. Follow the brief: fixture copy only, no invented metrics, no gradients, no emoji icons, and no framework/CDN/external assets in the eventual single-file build. Gentle humor belongs in specific helper copy, never in warnings.

## 9. Signature element, hero thesis, reference lock.
Signature element: the **paired owner frame and shared fact card**, with a tiny hand-drawn SVG cabinet key tag beside the service name. Hero thesis: “Every service keeps its own door; every shared fact keeps its source.” Reference lock: Airbnb’s calm listing/detail hierarchy (whitespace and rounded content framing, not travel imagery or booking UI) and Apple Home’s accessory-to-home state handoff (mechanic, not palette). Keep only one signature; the label illustration is a small accent, not a second hero.

## 10. Risks and UNKNOWNs.
This is synthetic mock data, never a real reading. Actual Connect protocol, browser-enforced embed isolation, permission enforcement, service-to-Worlds messaging, persistence/history after disconnect, and live-feed timing are UNKNOWN. The live feed must not imply real polling or provider health. Check color pairs and 200% reflow in implementation; ensure every state has text beyond color and remains usable when the embedded app is unavailable.

## 11. How it differs from C, and what it keeps
Unlike C’s cabinet bays and inset-bezel presentation, v7989 treats services as a plain, fixed-order register in a more everyday application workspace; its warm hospitality comes from generous spacing, a small key-tag drawing, and humane copy rather than a physical cabinet illusion. It keeps C’s persistent Home / Connect / Memory / Settings shell, clear service ownership, docked owner app and shared facts, honest fixture states, and a non-authoritative Worlds boundary.

## 12. Desktop and mobile layouts
**Desktop, 1440px:** persistent top shell navigation with the four destinations, compact “MOCKUP” marker, and live-feed toggle. Below, a constrained main canvas has the service register at left and selected service workspace at right. The first viewport shows service name/state, embedded app frame, shared facts, **#disconnect**, **#simulate-change**, and **#add-service** without opening a hidden menu. Home and Memory reuse the same fact rows, not separate summaries with divergent state. **Mobile, 390px:** bottom navigation for Home, Connect, Memory, Settings; service register and detail are distinct one-column screens with explicit Back, and selected-service actions stay near its heading. Keep the live toggle visible on the relevant Home/Connect view, and keep Disconnect on the first selected-service screen. Reorder to mobile reading sequence (shell nav, page heading/actions, app frame, facts); use safe-area insets, wrapping labels, 44px targets, and no horizontal scrolling. At both widths the visible MOCKUP label persists; at 768px the register may become a compact list above detail.

# CRITIQUE — v7989 "The Service Cabinet" (round 3)

Reviewed against `docs/vnext/concept-brief-v3.md`, `concept-brief-v2.md` (still in force), `reference/direction-C-DESIGN.md`, and `fixture/fixture.json`. Five gaps, most important first. ## 1. The fixture was misread, and it costs the concept its two best daily-use surfaces

**What's wrong.** §2 says: "Include **the only other fixture service, Nightly Backup**, only if needed for an error-state illustration." The fixture has **seven** services, not three. Beyond `media-shelf`, `front-door` and `notes-sync` there are also `garden-camera` (`unknown`, with `unknownReason`), `studio-printer` (`unavailable`, with `retry`: *"Retry last job"*, `lastError: "job rejected: no media loaded"`, `attempts: 1`) and `local-weather` (`not_configured`, empty `facts: []`, with `emptyReason`: *"No provider configured, so there are no facts to show."*). The doc picked the wrong one for the job: Nightly Backup is `stale`, not an error state. And **no retry affordance is designed anywhere in the document** — the fixture ships `retry` for two services, and integration requirement 5 (brief v2 §5) is precisely "a governed action hands off." A daily-use service cabinet with no retry button is not a daily-use cabinet.

**Why it matters.** Brief v3 §1 demands "an error state (a service that fails its test **or drops off**)" and a "first-run / empty state." Studio Printer is a printer that is reachable and *rejected the job* — a human-only retry that must hand off to Studio — which is the single most honest and most everyday interaction in the fixture, and it exercises requirements 4, 5 and 6 in one screen. Local Weather is the fixture's purpose-built zero-provider empty case (`emptyReason`), and the doc's own §6 promises "zero providers means no readings" without having a service to say it on. Garden Camera is the only record that carries `unknownReason`, so §6's "Unknown is stated in words with its fixture reason" currently has no subject.

**Concrete fix.** Add a section that pins the whole fixture roster and each service's role, verbatim from `fixture.json`:

| Service | Fixture state | What it must demonstrate |
|---|---|---|
| `media-shelf` — Media Shelf | `healthy` | quiet state; exact fixture summary |
| `front-door` — Front Door | `needs_attention` | governed handoff to Home (`app://home`); `lock-back-door` cross-view |
| `notes-sync` — Notes Sync | `unavailable` | provider failure ≠ local failure; added through Connect |
| `studio-printer` — Studio Printer | `unavailable` | **retry affordance**: `#retry-last-job`, human-only, renders as a handoff to `app://studio/printers`, shows `lastError` and `attempts: 1`, and after activation records a *mock review* only — it never changes `printer.status` or the error code in the fixture |
| `garden-camera` — Garden Camera | `unknown` | the only `unknownReason` state, said in words; the three facts stay `unknown`/`null` and are never blank |
| `nightly-backup` — Nightly Backup | `stale` | staleness with an 8+ hour gap; "Stale" is a label, not a colour |
| `local-weather` — Local Weather | `not_configured` | the honest empty state with `emptyReason`; "Add a provider" hands off to `app://settings/providers`; zero placeholder readings |

Then state the retry rule once, in §5: retry is `allowed: "human"` in the fixture, so Worlds renders it as a named control that hands off, never an in-Worlds mutation, and never as an agent-permitted action.

## 2. "Reactive" is asserted, not specified — there is no live-feed mechanism and no optimistic feedback at all

**What's wrong.** §6 gives the entire reactivity story one sentence: *"Live freshness ages from fixture timestamps; the feed is ON by default, occasionally marks a service stale, and updates Home, service and facts without reload."* No tick interval. No rule for recomputing age (the fixture is explicit: *"A viewer should recompute age from checkedAt rather than trusting this number"* — so a wall-clock offset has to be defined). No answer to **which** service goes stale, **when**, or **how it returns**. No bounded behaviour: a feed that "occasionally marks a service stale" with no return path drifts the prototype into a screen of stale rows within a minute of watching it. Worse, making a service stale means mutating `freshness.state` on a fixture record whose `_meta` says *"Concepts must not mutate the fixture."*

Brief v3 §4 asks for three distinct things and the doc delivers roughly one: the aging tick, **"actions give instant optimistic feedback and settle visibly"** (absent — `#simulate-change`, Publish, and Disconnect are all described as single atomic commits), and **"transitions between states are visible."** The only motion named anywhere is *"one gentle, one-shot label transition"* on connect. That is the thinnest possible reading of brief v3 §2's "a satisfying 'connected' moment," and a one-shot *label* change is the thing Emil's rulebook explicitly warns against (keyframes on rapidly-triggered UI — see gap 5).

**Why it matters.** Reactivity is the decision Rylee named first ("let's kick of the real rounds and have them keep in mind the more real application... and are reactive"), and the checker's contract requires `#live-toggle` to *actually* pause a feed. A sentence with no cadence, no reset, and no optimistic layer is not buildable as written — whoever builds this will invent four different numbers and the states will diverge from the DESIGN.md.

**Concrete fix.** Write a "Reactivity contract" subsection with numbers in it:

- **Cadence:** one tick every 2s, driving a volatile `ageSeconds` overlay computed as `now − checkedAt` against a stated `now₀`. Crucially, staleness lives in a **separate overlay object**, not on the fixture record: `overlay = { [serviceId]: { observedAgeSeconds, forcedState } }`. `forcedState` is the only field the feed ever writes; it is cleared and the record returns to its fixture state on reset or on pause-then-resume.
- **Escalation ladder:** fresh → stale after a stated age threshold; only Notes Sync (whose fixture `freshness.state` is already `stale`) and one rotating candidate may go stale, chosen from a fixed cycle; a forced state always auto-expires after N ticks so the shell returns to a legible baseline. The feed never moves a service to `unavailable`, `unknown` or `needs_attention` — those are authored states, not ticks.
- **Optimistic + settle, per action:** Publish → the register row appears immediately as "Connecting…" (dimmed, `unavailable`) and settles to the fixture state on the next tick. Disconnect → the row collapses immediately and the remaining rows reflow; the "what disappeared" notice persists. Retry → the control shows "Handing off…" and settles to a named mock-review line. `#simulate-change` → the fact value and the attention count both change in one commit, and both animate out and in.
- **Transitions:** name the transition that crosses the Connect→register boundary (the flow's last step hands off; the new row enters from the same edge with opacity + 8px translateY, ~180ms, `cubic-bezier(0.23, 1, 0.32, 1)`). Under `prefers-reduced-motion` the same change happens instantly with an opacity crossfade only, and the feed keeps ticking.
- **Honesty:** a persistent line beside the toggle — "Simulated clock; these are MOCKUP readings, not a live check" — so the visible UI, not just this document, refuses to imply real polling.

## 3. The difference from C is nominal: v7989's signature element is C's signature element

**What's wrong.** C §9 names its signature as *"the static inset screen and shared fact card dock together inside the selected owner bay."* v7989 §9 names its signature as *"the paired owner frame and shared fact card."* That is the same artifact under a new noun. The four shell destinations (Home / Connect / Memory / Settings) are C's; the Connect lifecycle in §2 is C's six steps; §7's borrows are C's; §6's state inventory is C's. §11 — the paragraph brief v3 asks for — argues for what v7989 *isn't*: *"a plain, fixed-order register... rather than a physical cabinet illusion."* Removing a metaphor is not designing an alternative, and brief v3 says plainly "Use C as the starting direction, **do not clone it**."

The whimsy is attached to the abandoned metaphor. §1 offers "a tiny inline-SVG cabinet-label illustration" and §9 a "tiny hand-drawn SVG cabinet key tag," while §11 disowns the cabinet and §7 insists the register is "not a map, route diagram, or unfolding place." A key tag beside a list row has nothing to key. With the cabinet gone, the warmth is a decorative sticker on a generic workspace, and the concept has *less* personality than C while claiming more.

**Why it matters.** If a reviewer screenshots v7989 and C side by side and can't say which is which, the round produced one concept. And "generous spacing and humane copy" is not a thesis — it's a disposition.

**Concrete fix.** Pick one structural move C does not have and make it load-bearing, then move the signature onto it. One workable direction, offered because the doc should argue its own: **the fact card is the artifact, the service screen is its transcript.** The register row carries the single fact that drove the current service state inline (Front Door → "Back door · unlocked · 47 min"); opening the service shows that fact's provenance — who observed it, when, who may act — and Memory shows the same fact with the same permissions, so the person can trace one value in one direction (row → why) instead of C's two docked columns that say the same thing side by side. Then re-home the whimsy: the SVG becomes a small *provenance mark* on each fact row (a filled dot for local-observed, an outlined one for external, a hairline break for unknown) with one line of kind copy ("No source has answered since 11:02 — we're not guessing."), and §11 gets a paragraph about that move, not about absent cabinet illusion.

## 4. Settings is one clause, and the 390px first screen has no stated budget

**What's wrong.** Brief v3 §1 requires "a settings screen" as one of the things that separate a real application from a concept. v7989 §3 gives it eight words: *"Settings groups appearance/comfort and the live feed."* No rows, no labels, no states, no defaults. "Appearance/comfort" is undefined — it could be three toggles or nine. Meanwhile the live-feed control is specified **twice in two different places**: §12 puts it in the desktop top bar, and §12 again says "keep the live toggle visible on the relevant Home/Connect view" for mobile, while §3 files it under Settings. A control with two possible homes is a control whose state will diverge.

The mobile layout also stops one step short of the requirement. Brief v3 §3 wants mobile with "its own reading order," "not a squeezed desktop." §12 gives a bottom bar, one column and a Back link — fine — but then appends, at the end of the mobile paragraph, *"at 768px the register may become a compact list above detail,"* which is the two-column desktop collapsed, i.e. exactly the squeezed desktop, offered as the tablet answer. And the mobile first screen is unbudgeted: heading + actions, an embedded app frame, a fact card with three facts, `#disconnect`, `#simulate-change` and `#add-service` are a very long 390px page, and the doc never says what is above the fold. It does assert `#disconnect` is on the first screen, but "first screen" is doing quiet work at 390px.

**Why it matters.** Settings is where a real application shows its defaults and its taste; leaving it a clause means the most-visited-when-idle screen has no design. And the mobile screen is the layout brief v3 §3 says most concepts get wrong.

**Concrete fix.**

- Enumerate Settings as a table with exact rows, defaults, and what each changes: `Live feed` (default On, mirrors `#live-toggle`), `Pauses with the tab when hidden` (default On), `Motion` (`Full` / `Reduced`, prefilled from `prefers-reduced-motion`), `Text size` (`Standard` / `Large`, applied as a root font-size step), `Comfort spacing` (`Standard` / `Roomier`, an 8px-step scale change), `Mark everything as read` / `Dismiss all` where relevant, plus a plain-language "About this MOCKUP" block carrying the fixture's `syntheticNote`. Every row states whether it is fixture-backed or a local display preference — no preference may alter a fact's value.
- Put `#live-toggle` in **exactly one place** (top bar on desktop, above the register on Connect on mobile) and have Settings show it as a row that reflects and controls the same state, described as one control in one source of truth.
- State the 390px first-screen budget explicitly: on the service screen, above the fold are the page heading with the service name, its state word, and `#disconnect`; the embedded app frame starts at or below the fold with a collapsed-preview summary above it; facts, `#simulate-change` and `#add-service` scroll beneath. Say which control is focused on entry and give the reading order as an ordered list.
- Move the 768px sentence into its own line under a tablet heading, and make it a real tablet answer (register as a horizontal two-up card row above a full-width detail, not a collapsed column pair).

## 5. The OpenDesign starting point is invoked by name, then overridden; neither system actually shapes the design

**What's wrong.** §8 says "Apply Emil's purposeful, brief, interruptible feedback" and "the craft rulebooks' anti-slop constraints, limited accent, readable type…" — adjectives and a bundle citation, not decisions. Nothing from `skill-emil-design-eng.md` survives into the document as a number. That skill's load-bearing rules are precisely the ones a reactive shell needs and none are stated: the frequency table (tens-of-times-a-day actions get *drastically reduced* motion; 100+/day gets *none* — which is the rule that decides whether `#live-toggle` and Back animate at all), *"never animate keyboard-initiated actions,"* UI animations under 300ms, custom easing curves (`cubic-bezier(0.23, 1, 0.32, 1)`), `transform: scale(0.97)` press feedback, and *use CSS transitions, not keyframes, for interruptible UI* — which §6's "one-shot label transition" directly violates.

`ds-airbnb` fares worse. The document takes `#222222` near-black, hairline separators, rounded corners, 8px base and coral-as-primary, and overrides away or ignores everything that made the system specific: the sticky right-rail panel that **collapses to a bottom-anchored bar on mobile** — which is precisely the desktop→mobile collapse brief v3 §3 asks to design on purpose; the 50% circular back button, which is exactly the "explicit Back link" §3 requires at 390px; three-layer elevation on floating panels; the no-400-weight rule (the doc specifies fonts as "system sans fallbacks" and says nothing about weights, so the build will default to 400); and the system Don'ts the doc breaks by substitution without saying so. C's DESIGN.md §8 at least lists concrete tokens (`#111827`, `#FA3C00`, the 4/8/12/16/24/32 scale, the 12/14/16/20/24/32 type scale) and names its measured contrast fallbacks. v7989 names none.

**Why it matters.** Brief v2's lever-1 rule is "bind to a design system; **do not invent values outside it**" — but a system you override in every characteristic move isn't binding, it's a mood. And the two craft questions (5a, 9–12 from `DESIGN-QUALITY-GUIDE.md`) are about decision coverage: right now neither assigned file makes a single decision the document can be checked against.

**Concrete fix.** Replace §8 with a pinned table of 8–10 named token decisions with hex values, and a second table of 4 named rule citations, e.g.:

- `Emil — frequency table`: `#live-toggle`, Back, and tab switches animate at 0ms or opacity-only (tens/day); only the connect confirmation and first-run invite get 180–240ms (rare/first-time). State this rule and apply it to the §6 motion list.
- `Emil — transitions over keyframes` on anything that can fire twice in a row (publish, disconnect, simulate-change); `scale(0.97)` on `:active` for every pressable, gated behind `@media (hover: hover) and (pointer: fine)` for hover.
- `Emil — reduced motion` = opacity and colour keep, transform and position go; data keeps ticking.
- `ds-airbnb` carried: sticky right-rail at 1440 collapsing to a bottom-anchored bar at 390 for the service workspace; 50%-radius circular Back control; the three-layer `rgba` stack reserved for the owner-app frame only; body weight 500 with no 400; 8px base and the 14/16/21/28 type roles; Rausch reserved for the single primary action per screen (which means coral appears on Connect's publish and nowhere else).
- `ds-airbnb` deliberately overridden, stated as overrides: `#ffffff` canvas → a named warm low-glare neutral with its hex, justified for a screen read at night; travel photography and 3D category icons out, per the no-external-assets floor.
- Contrast: give the coral-on-warm-neutral and every state-word pair its measured ratio, and name the drop order (fill → text → non-text marker only) if a pair fails. C did this; v7989 deferred it to §10, which is where it fails at review time.
- Cite the rulebooks individually (`anti-ai-slop`, `color`, `typography`, `laws-of-ux`, `state-coverage`, `accessibility-baseline`, `animation-discipline`) with the one rule taken from each, rather than listing them as a bundle.
