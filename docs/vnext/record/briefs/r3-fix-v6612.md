## Your DESIGN.md

# v6612 — The Welcome Shelf

## 1. Metaphor in one line, and the main gesture.
Worlds is a small, well-kept home for independent services: scan what needs you, then open the named service beside the facts it shares. Main gesture: select a service and move between its own workspace and its shared facts. A tiny inline SVG house-wren perches beside the greeting; it is decoration, never status.

## 2. Integration model: how a service plugs in, where it lives in the shell, how its facts flow.
Start with exactly Media Shelf (`media-shelf`, `healthy`) and Front Door (`front-door`, `needs_attention`). `#add-service` opens a six-step Connect flow for Notes Sync (`notes-sync`, `unavailable`): discover → enter a credential reference only → safe test → preview the three fixture facts → choose which facts to publish → publish. Secret values are rejected; no provider call occurs in this mockup. Each service owns its app, actions, and data; a shared local store keyed by fixture fact ID feeds Home, its service screen, and Agent facts. `#simulate-change` applies only the fixture’s `lock-back-door` example: Back door becomes `locked`, Front Door becomes `healthy`, and attention count becomes zero in all three views. This is a mock handoff, not a real lock command.

## 3. Navigation between Worlds and a service (phone and desktop).
Persistent shell navigation is Home, Connect, Memory, Settings. A service’s screen is inside Worlds, with its owner and “Open [owner] app” fallback visible. Navigation, Back, and status remain Worlds-owned around the embedded service. Keyboard focus follows semantic source order; service selection moves focus to its heading and Back restores focus to the invoking control.

## 4. The embedded-app frame (sandbox, fallback, what the shell keeps around it).
Show the owner app in a clearly titled, bounded app frame beside a Worlds-owned fact panel. Keep the owner label, state, and fixture fallback link visible: Media Shelf → “Open Media app” (`app://media`); Front Door → “Open Home app” (`app://home`); Notes Sync → “Open Memory app” (`app://memory`). No credential is passed into the frame. Actual embed protocol, browser isolation flags, and messaging are UNKNOWN. If embedding fails, retain the facts and explain the failure beside the owner link. Approvals hand off to Project Home; other actions go to their owner.

## 5. The agent/human shared-facts model (source, freshness, who sees, who acts).
Home cards, service facts, and Agent facts read the same records. Show value, source, observed/checked time, freshness as words, and separate “Agent can see,” “Human can see,” and “Who can act” fields. Preserve independent permissions: `frontdoor.back-door` is Agent read / Human act; `frontdoor.unlocked-for` is read by both; `frontdoor.guest-code-used` is Human read and Agent none, with its fixture reason shown in a named disabled control. Notes Sync’s unavailable provider fact does not erase its live local pending count or stale last-sync fact.

## 6. States: empty/first run (zero services, zero providers), quiet, needs-you, stale, unknown, disconnected.
First run shows an inviting empty shelf, local Worlds/Memory baseline, and one “Connect a service” action; no invented readings. Quiet uses Media Shelf’s exact `healthy` label. Needs-you uses Front Door’s “Needs a human” state and fixture explanation. Include Nightly Backup (`stale`), Garden Camera (`unknown`), Studio Printer (`unavailable`), Notes Sync (`unavailable`), and Local Weather (`not_configured`) when browsing the fixture; name the last observation or reason and what still works. A failed test identifies Notes Sync and offers retry. Disconnect says what service will be removed and leaves the remaining shell usable; retention history is UNKNOWN. State words and recovery copy never rely on color.

## 7. Borrowed from Homarr / Dashy / HA cards / MCP ext-apps, and what is deliberately different.
Borrow Homarr’s integration reused across views, Dashy’s in-place app opening, Home Assistant cards’ shared state, and MCP ext-apps’ contained UI boundary. Unlike a widget dashboard or tool host, this is a personal front door: the owner is named, facts have explicit provenance and separate permissions, and consequential choices return to the owning app. No provider becomes Worlds’ product model.

## 8. Your OpenDesign starting point (skill + design system) and how you used it; which guide rules you applied.
Starting point: `skill-ui-ux-pro-max.md` and `ds-duolingo.md`. The skill file is catalog-only; its full upstream search workflow is not bundled, so no unavailable pattern library is claimed. From Duolingo, keep friendly rounded headings, a restrained leaf-green action cue, and a single warm wren accent; discard high-saturation coverage, chunky button shadows, oversized lesson type, and gamification. Use calm neutral surfaces, readable sans-serif type, and consistent 4/8/12/16/24/32 spacing. Apply the guide’s one-job hero (the selected service with its live facts), one signature element (the wren beside a clear “All yours / Needs a human” greeting), named reference mechanics rather than copied palettes, real fixture copy, explicit state coverage, and no gradients, emoji icons, or invented metrics. Keep visible MOCKUP labeling.

## 9. Signature element, hero thesis, reference lock.
Signature: a tiny line-drawn wren offers one kind, contextual sentence beside the service summary; it never animates as telemetry. Hero thesis: “Your services keep their owners; Worlds helps their facts make sense together.” Reference lock: Apple Home’s accessory-to-owner handoff and Homarr’s integration feeding multiple surfaces; borrow mechanics, not visual language.

## 10. Risks and UNKNOWNs.
The Connect API, safe-test semantics, service embed protocol/isolation, real action authorization, and disconnect history are UNKNOWN. All values are synthetic fixture data and the UI remains MOCKUP. Validate actual contrast pairs, mobile safe areas, keyboard focus, and 200% reflow in implementation. Live freshness is simulated and must be labeled as such, never presented as a real observation.

## 11. How it differs from C, and what it keeps
C’s service cabinet pairs a fixed owner bay with a docked app and shared fact card. This concept keeps the persistent Home / Connect / Memory / Settings shell, clear ownership, honest fixture states, and adjacent owner app plus shared facts, while shifting the main gesture to a welcoming daily front door: a concise attention-first home leads into full service workspaces, with one restrained wren detail supplying warmth. It does not reproduce C’s cabinet/bay metaphor or its fixed register as the organizing visual.

## 12. Desktop and mobile layouts
**Desktop, 1440px:** persistent left navigation rail; centered content column with a first-day/attention summary and service list; selected service opens a two-column workspace with embedded owner app and shared facts side by side. Settings is a real shell destination, with live-feed pause/resume visible in its status controls and on the home freshness line. **Mobile, 390px:** compact top identity and a fixed, safe-area-aware bottom bar for Home, Connect, Memory, Settings; one-column reading order is greeting/attention, service summary, owner app, then facts and actions. Selecting a service opens its own full-width screen with an explicit Back control. Connect is a sequential full-screen step flow. Keep `#add-service`, `#disconnect` for the selected service, `#simulate-change`, and `#live-toggle` visible on the first Home screen; disconnect opens a confirmation whose action is labeled “Disconnect.” Targets are at least 44px, no sideways scrolling, focus is visible. `#live-toggle` is ON by default and pauses/resumes simulated freshness updates in every view. State changes settle with a brief 150ms opacity/color cue and a text update; reduced-motion removes transform effects and keeps all state legible without animation.

## CRITIQUE.md (another engine)

# v6612 "The Welcome Shelf" — critique (round 3)

Five gaps, most important first. This is a strict pass: §1–§5 of the concept are accurate against `fixture.json` (states, `crossViewExample`, and the three `frontdoor` permission rows all check out), and §8 is honest that `skill-ui-ux-pro-max.md` is catalog-only. The problems below are not errors of fact; they are places where the DESIGN.md *names* a thing the round-3 brief demands and then declines to decide it.

## 1. The OpenDesign design system is used by subtraction, not used. (most serious)

**Wrong.** §8 says it keeps "friendly rounded headings, a restrained leaf-green action cue, and a single warm wren accent" and discards "high-saturation coverage, chunky button shadows, oversized lesson type, and gamification", then substitutes "calm neutral surfaces, readable sans-serif type, and consistent 4/8/12/16/24/32 spacing". Read against `docs/vnext/od-pack/ds-duolingo.md`, almost every *defining* trait of that system is the thing being deleted: §1 of the DS makes Owl Green `#58cc02` present on 30%+ of the surface with a 4px `#58a700` bottom edge on every interactive element, 2–3px `#e5e5e5` borders, 16–20px card radii, Feather Bold 800 headings, big type. The concept keeps none of those and names no replacement system. Worse, DS §7 "Usage Guardrails" says it explicitly: *"Keep the high-saturation owl green, chunky bottom shadows, and rounded lesson geometry together; flat green buttons alone do not read as Duolingo."* The concept does precisely the thing its own assigned DS forbids. And "leaf-green" is not a token in `ds-duolingo.md`; the nearest is `#58cc02`, which §8 rejects. "Calm neutral surfaces" is an invented system wearing the assigned system's name.

**Why it matters.** Brief v2 §27 makes this a floor, not a preference: *"Bind to a design system (lever 1): each concept has an assigned design system; do not invent values outside it."* Brief v3 §29 asks the system to *shape* the concept. As written, the OpenDesign input is a permission slip to go neutral — a round-2-shaped answer ("calm structure" was C's whole identity) wearing round-3 vocabulary. And the one place a Duolingo grammar would have genuinely helped is the part the concept disarms: this system's mascot-as-character, 320ms unlock easing, and Duo-in-errors are exactly "a satisfying 'connected' moment" and "a gentle motion on a state change" (brief v3 §2).

**Fix.** Commit to a named *subset* of `ds-duolingo.md` and print the tokens in §8: 16px card / 12px button radii, 2px `#e5e5e5` borders with a 4px `#58a700` bottom edge as the single action affordance, `#dbf8c5` as the success/attention surface, the Feather-Bold-fallback 800 headings at a *reduced* display size, `#3c3c3c`/`#777777` ink, the 4/8/12/16/24/32 scale, and DS §6 motion (180ms press, 320ms unlock) reserved for exactly two events: publish/connected and a fact settling. Because Owl Green `#58cc02` is ~2.3:1 against white, state the contrast rule up front — green only as a non-text edge and the `#dbf8c5`/`#58a700` pair for filled surfaces with `#3c3c3c` text — and note the measured ratios, since brief v2 §23 floors contrast at 4.5:1. If the warmth has to go calm, get there *inside* the Duolingo grammar (soft fills, gentle radii, low-saturation green usage) rather than by deleting it.

## 2. Navigation is a list of four names; three destinations have no design, and the first screen has no selection.

**Missing.** §3 and §12 define Home, Connect, Memory, Settings and then specify screens for only Home, the selected service, and Connect. **Memory** — a persistent top-level destination in both layouts — is never described in any section: no content, no layout, no reason it is not Settings. **The agent-facts view is nowhere.** §2 and §5 both treat "Agent facts" as a real view ("a shared local store keyed by fixture fact ID feeds Home, its service screen, and Agent facts"), but no section says where it lives, how you navigate to it, or what it looks like at 390px. §12's mobile order (greeting/attention, service summary, owner app, facts) has no slot for it. **Settings** gets one sentence (§12: "live-feed pause/resume visible in its status controls"). And nothing states what is *selected* at first paint, which is what makes `#disconnect` show up: §12 asserts "Keep … `#disconnect` for the selected service … visible on the first Home screen", but §3 describes selection as something the user does, so at first paint there may be no selected service and the checker item (brief v3 §20: *"`#disconnect` is visible on the first screen for the currently selected service (not hidden until something is opened)"*) fails.

**Why it matters.** This is the "real application you would use every day" test (brief v3 §1) and it is where the concept is thinnest. Three of the four top-level destinations are stubs, and integration requirement 4 (brief v2 §18: one change updates home, the service surface, **and the agent-facts view**) is unverifiable if there is no path to the third view — which is precisely the view an automated checker will look for after `#simulate-change`. Brief v3 §1 asks for "a settings screen" as a named deliverable; a sentence in §12 is not a screen.

**Fix.** Give each destination a real decision. **Memory:** the local baseline that survives a disconnected provider (this is where `sync.local-pending` = 3 notes and `sync.last-synced` live, exactly as brief v2 §16 requires local data to be preserved) — with a distinct layout at 390 (list-then-detail) and 1440 (two columns, pending vs. last successful sync side by side). **Agent facts:** make it a first-class screen reachable from the Home service row and from the service workspace, listing every fact ID with source, freshness, and the three permission fields separated; on mobile, a stacked row where the permission triple is the last line, not a truncated badge. **Settings:** give it real controls that are not pause — a per-fact "the agent may see this" list mirroring §5's permissions (which is where `frontdoor.guest-code-used`'s `none` and its verbatim reason earns its home), reduced-motion status, and fixture provenance ("all values synthetic"). **Default selection:** pin Front Door as selected at first paint (it is `needs_attention`, so the hero thesis and `#disconnect` both work immediately) and say so in §12, with Home's service list making the selection visibly shared between the list, the workspace, and the mobile detail screen. Also pick one owner for pause state so the Home freshness-line toggle and the Settings control cannot drift.

## 3. Reactivity is specified as a label, not as a policy: no drift, no optimistic state, no pause semantics.

**Missing/wrong.** §12's whole reactive story is "a brief 150ms opacity/color cue and a text update" and "`#live-toggle` … pauses/resumes simulated freshness updates in every view". Three requirements in brief v3 §4 are unanswered: (a) *"occasionally moves a service to stale"* — no drift policy exists; the tick only ages "checked 12s ago", and no connected service is ever moved to `stale`; (b) *"Actions give instant optimistic feedback and settle visibly"* — the concept names the transition but no action. The governed `lock-back-door` handoff (§4: "Approvals hand off to Project Home") has no pending state: does the fact read "Locking — waiting on Home" for a beat and then settle to `locked`, or does it flip instantly with no pending? `#disconnect` and publish have no described pending/failure state either. (c) `#simulate-change` and `#live-toggle` interact undefined — what happens if you simulate while paused, and does pausing freeze the age counter or only the re-checks?

**Why it matters.** "Reactive" is Rylee's stated reason for the real rounds (brief v3 §6, and the v2 §9 quote about static images not counting). A feed that only increments a number is a clock, not a live feed: the point is that a *view you are not looking at* changes and the one you *are* looking at agrees. And a handoff that changes a real fact's value — back door goes from `unlocked` to `locked`, attention count to 0 — is the single most consequential interaction in the prototype; showing it without a pending state teaches the reader that the agent can just do it, which is the opposite of brief v2 §19.

**Fix.** Pin four decisions in §12. (1) *Drift:* after N ticks the oldest-checked `live` service moves to `stale` with its real reason word and a one-line announcement, and names which fixture service it affects — that is what makes `#live-toggle` worth toggling. (2) *Optimistic:* `lock-back-door` renders `frontdoor.back-door` as `Locking… (waiting on Home app)` with the Agent row marked pending, then settles to `locked`/`healthy`/count 0 on the same tick as the fact store, using the 320ms unlock easing; publish and disconnect get the same pending-then-settle shape, with the disabled-while-pending state announced to assistive tech. (3) *Pause semantics:* pausing freezes age recomputation and drift, greys the freshness line with the word "feed paused", and leaves `#simulate-change` working (it is an explicit human action, not a feed event); resuming states the elapsed gap ("paused 40s — freshness may have moved") so it never pretends nothing happened. (4) *Honesty:* keep the §10 "simulated" label on the feed itself, not only in the risks section.

## 4. The whimsy is disarmed at the point of definition, and the metaphor collides with a fixture service name.

**Wrong.** §1 makes the wren "decoration, never status"; §9 makes it offer "one kind, contextual sentence … it never animates as telemetry"; §12 gives the whole motion budget 150ms. Three separate prohibitions, all aimed at the one element brief v3 §2 exists to license: *"Small, specific, delightful moments: kind micro-copy, a tiny illustration or character accent drawn in inline SVG, a gentle motion on a state change, a satisfying 'connected' moment."* There is no connected moment: publish in §2 is a step that produces a service. And the metaphor itself is shaky — §1 calls Worlds "a small, well-kept home", §6 an "inviting empty shelf", while §11 claims the concept "does not reproduce C's cabinet/bay metaphor or its fixed register". A shelf is a cabinet with a different noun, and §1's main gesture ("select a service and move between its own workspace and its shared facts") is C's gesture, restated. Worst of all, "front door" is a fixture service (`front-door`, "Needs a human") and §11 says the shift is "to a welcoming daily front door": the shell's headline noun is also the name of the service that is currently asking for a decision.

**Why it matters.** Brief v3 §2 asks for warmth *laced in*, not a theme park — but disarming the character in three places is not lacing. And §11's difference-from-C paragraph is the one section a reviewer is required to believe (brief v3 §10); a claim the concept's own §1 and §6 contradict will read as spin, which costs credibility on the parts that *are* real (honest states, clean permission model, no invented readings).

**Fix.** Let the wren do exactly one job and let it be the one thing the round asks for: it reacts to state, and only in ways that never carry meaning alone. Concretely — the greeting wren is static and present at all times; on publish it does the one 320ms settle and a single short line ("Notes Sync is on the shelf. Three notes are waiting."); on `#simulate-change` it goes still and quiet while the pending state shows; on pause it sits. Each of those is a *moment*, none is telemetry, and none is status colour. Rewrite §11 honestly: keep C's shell and the owner-plus-facts pairing (Rylee liked them), drop "shelf" and "front door" as metaphor nouns, name the actual delta — attention-first home leading into per-service workspaces, with one warm character and no furniture metaphor at all. If "front door" survives as copy, it must be disambiguated everywhere it appears near the Front Door service ("Welcome back" / "What needs you" is cheaper and clearer).

## 5. The claimed state coverage is unreachable, and first-run / error states have no path in the prototype.

**Missing.** §2 pins the shell to exactly `media-shelf` and `front-door`, with `#add-service` opening a Connect flow for `notes-sync` only. But §6 then claims coverage of Nightly Backup (`stale`), Garden Camera (`unknown`), Studio Printer (`unavailable`) and Local Weather (`not_configured`) "when browsing the fixture" — there is no described UI for browsing the fixture, and Discover is specified as listing Notes Sync. So the stale / unknown / not_configured states that brief v2 §23 and §19 require, and that §6 advertises, cannot be seen. §6's "First run shows an inviting empty shelf" has the same problem in reverse: the prototype starts with two services and `#disconnect` removes one at a time, so zero-services is never reachable either. And the retry story is conflated — §6 ties "A failed test identifies Notes Sync and offers retry" to the *Connect* safe test, while the fixture's `retry` object is a service-level, human-allowed action (`studio-printer` "Retry last job" → Studio, `notes-sync` "Check provider now" → Memory) that brief v2 §19 says must hand off to the owning app.

**Why it matters.** Brief v2 §13 turns on round 1's exact failure: *"they seem to not get the fact it needs to be integrated, they seem like concepts on a page."* A states table you cannot navigate to is a page. Unreachable first-run and unreachable unknown/stale is worse than not claiming them — it reads as coverage pasted from the fixture's vocabulary rather than designed, which is the exact impression Rylee rejected. C avoided this by explicitly saying unknown "is not inferred for these composed services"; v6612 claims the coverage and cannot show it, and §10 does not list it as a gap.

**Fix.** Make Discover list all five remaining fixture services with their verbatim ids, names, states and owners, so `notes-sync`, `nightly-backup`, `garden-camera`, `studio-printer` and `local-weather` are each connectable through the same six steps — that makes stale, unknown, unavailable-with-retry and not_configured all reachable in the prototype, and Local Weather's empty `facts: []` naturally produces the honest empty-provider state. Then add one first-run affordance the reader can actually see: since the prototype starts populated, put a "Reset to first run" in Settings (or make the very first paint first-run, with a "Load the example shelf" action) so zero services, zero providers and the Connect invitation are demonstrable rather than asserted. Finally split retry from the safe test: the Connect failure offers a retry of the *test*, while each service's `retry` is an owner-app handoff with the fixture's label and `allowed: human` shown as a real, disabled-when-not-permitted control.
