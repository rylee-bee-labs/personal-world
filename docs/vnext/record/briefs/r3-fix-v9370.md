## Your DESIGN.md

# v9370 — The service workbench

## 1. Metaphor in one line, and the main gesture.
Worlds is a welcoming workbench with clearly named service stations; choose a station to see its own app alongside the facts Worlds shares. The main gesture is **select a service, then move between its app and the shared facts without losing your place**. Reading this as a daily personal application for one person, with calm structure, small crafted warmth, and a restrained workshop language. OpenDesign dials: variance 5, motion 2, density 4.

## 2. Integration model: how a service plugs in, where it lives in the shell, how its facts flow.
Start with exactly `media-shelf` (Media Shelf, `healthy`) and `front-door` (Front Door, `needs_attention`); select Front Door by default so its state and `#disconnect` are visible immediately. `#add-service` starts Notes Sync (`notes-sync`, `unavailable`) through Discover → Credential reference → Safe test → Preview → Choose what to publish → Publish. Accept a reference, never a secret; test failure is explicit and offers retry or back, while preserving the fixture’s local notes. Preview `sync.provider-reachable` (`unavailable`), `sync.local-pending` (3 notes, `live`), and `sync.last-synced` (`stale`). Facts flow by ID from one in-memory store to Home, the service station and Agent facts. `#simulate-change` applies the fixture’s `lock-back-door` example: `frontdoor.back-door` becomes `locked`, Front Door becomes `healthy`, attention count becomes 0, and all three views update together. This is a mock handoff/review only; Worlds does not operate the lock. Disconnect confirms with a button labelled “Disconnect”, removes the selected station and embedded app, and leaves the shell and other stations available.

## 3. Navigation between Worlds and a service (phone and desktop).
Persistent primary destinations are Home, Connect, Memory and Settings; service stations are reached from Home and Connect. On desktop, a narrow left navigation rail stays put while Home’s service register and selected service workspace fill the main area. Service actions belong to the owning app; approvals hand off to Project Home. On mobile, a fixed bottom bar holds the four Worlds destinations; selecting a station opens its own full-screen detail with a clear Back control and a reading order of title/state → owner app → facts → actions. Preserve semantic source order, 44px targets, visible keyboard focus and safe-area padding. Settings includes live-feed preference and motion comfort.

## 4. The embedded-app frame (sandbox, fallback, what the shell keeps around it).
Show the owner’s app in a bounded, clearly labelled frame beside or above the Worlds-owned fact surface. Keep Worlds navigation, service name/state, and the owner fallback visible around it: “Open Media app” (`app://media`), “Open Home app” (`app://home`), or “Open Memory app” (`app://memory`). If an embedded app cannot load, state that plainly and retain facts plus fallback. No credential value enters the frame. Exact embed protocol and browser-enforced isolation remain UNKNOWN; no mock action claims a real external change.

## 5. The agent/human shared-facts model (source, freshness, who sees, who acts).
Every fact row shows its literal value or explicit `unknown`/`unavailable`, source, checked/freshness wording, and separate “Agent can see”, “Human can see”, and “Who can act” fields. `frontdoor.back-door` is agent-read/human-act; show its fixture reason and route action to Project Home. `frontdoor.guest-code-used` shows human-read and a named disabled agent access control with its exact fixture reason, never exposing `visitor-3` to the agent. Other fixture permissions remain independent. Agent facts is a real view of these same records, not a second store. The live feed starts on; `#live-toggle` visibly pauses/resumes age updates, and a modest tick may make a service stale. State words accompany every visual cue; reduced motion removes transitions, not data updates.

## 6. States: empty/first run (zero services, zero providers), quiet, needs-you, stale, unknown, disconnected.
First run shows no invented readings, a local Worlds/Memory baseline, and a clear Connect invitation; zero providers means zero provider facts. Quiet uses Media Shelf’s fixture summary. Needs-you uses Front Door’s exact summary and attention reason. Notes Sync test failure keeps “local notes still work” distinct from provider unavailable. Stale, unknown, unavailable and not configured are explicit words with fixture explanations; blanks never imply health. Disconnect names what left and says its app is no longer available here; history retention is UNKNOWN. A small inline SVG workbench sprout marks a successful connection, with kind copy (“All set; Notes Sync has a place here.”), never status by illustration alone. MOCKUP is always visible. Default state is low-stimulation; no shimmer or looping motion.

## 7. Borrowed from Homarr / Dashy / HA cards / MCP ext-apps, and what is deliberately different.
Borrow Homarr’s one integration feeding multiple surfaces, Dashy’s in-place app opening, Home Assistant cards’ readable state, and MCP ext-apps’ contained app boundary. Keep service ownership explicit and facts shared across human and agent views. The workbench uses a linear register and one selected station, not a dashboard widget wall, a map, or a cabinet of repeated bays; it makes the small act of pairing an owner app with its shared facts the organizing gesture.

## 8. Your OpenDesign starting point (skill + design system) and how you used it; which guide rules you applied.
Starting point: `skill-taste-skill.md` + `ds-skeumorphism.md`. The skill says its marketing-page patterns do not govern dense product UI or multi-step forms, so borrow its anti-default and craft discipline only; this brief and Worlds contracts govern application structure. Use skeuomorphism’s playful physical cue as one flat, labeled work surface and a tiny inline SVG sprout, not textured panels or pressable fake hardware. Keep its spacing/type scale and `#111827` text; treat `#FA3C00` as a restrained accent only after contrast review, never as the sole state signal. Avoid large pure-white surfaces per Accessibility contract; use a soft, low-glare neutral field. Apply one consistent shape system, concise fixture copy, visible focus, static loading, named states, 44px targets, keyboard access, 390px reflow and reduced-motion behavior. No external fonts/images, invented values, gradients, emoji, or decorative motion.

## 9. Signature element, hero thesis, reference lock.
Signature: the paired “owner app / shared facts” work surface, joined by a narrow labeled seam that makes ownership and shared truth legible at a glance. Hero thesis: “Every service keeps its own hands; Worlds keeps the shared picture.” Reference lock: Homarr 2.0’s integration reused across surfaces, and Apple Home’s accessory-to-home state handoff; borrow mechanics, not their visual language.

## 10. Risks and UNKNOWNs.
Connect discovery protocol, credential-reference format, actual embed isolation, service messaging, and disconnect history behavior are UNKNOWN. The fixture is synthetic; label the concept MOCKUP and do not imply readings are real. Check text, control, and focus contrast in the eventual implementation. App handoffs and the lock example are demonstrative only.

## 11. How it differs from C, and what it keeps
C’s cabinet bays become a continuous workbench register and an owner/facts workspace, so the signature is the labeled seam joining an app to its shared facts, not a cabinet or inset bezel. It keeps C’s persistent Home / Connect / Memory / Settings shell, explicit service ownership, docked owning app, shared fact card, honest state words, and calm focus on one selected service. Warmth comes from a tiny sprout and humane confirmation copy rather than changing the application’s structure.

## 12. Desktop and mobile layouts
At 1440px, keep a 224px navigation rail, a roughly 300px service register, and a flexible workspace with the embedded owner app beside the shared-facts panel; keep service title, state, and `#disconnect` visible on the first screen. At 390px, use the four-item bottom navigation, a single-column Home register, then a dedicated service detail with Back; place the owner app first and facts immediately after, with actions including `#disconnect` visible without opening a secondary panel. `#add-service` is a prominent Connect action, while `#simulate-change` and `#live-toggle` remain visible in the current service/facts view. No sideways scrolling; long values wrap, controls stay at least 44px, and the facts panel follows the app in reading order. At both widths, show `#add-service`, `#disconnect`, `#simulate-change`, `#live-toggle`, and the MOCKUP label in their relevant first-screen context; on Home, `#disconnect` targets the initially selected Front Door service.

## CRITIQUE.md (another engine)

# Critique — v9370 "The service workbench"

Critique of `docs/vnext/round3/v9370/DESIGN.md` against `concept-brief-v3.md` (which keeps all of `concept-brief-v2.md` in force). Five gaps, most important first. Not graded generously.

## 1. It is C with the nouns swapped — the required difference is stated, not designed

**What is wrong.** v3 says "Use C as the starting direction, **do not clone it**." Compare the two documents section by section and the structure is identical: C §3 and v9370 §3 are the same persistent Home / Connect / Memory / Settings rail, the same "selected bay fills the main area", the same 390px "register becomes a one-column list, a selected detail replaces it, Back". C's layout in v9370 §12 is unchanged — rail, register, workspace with the owner app beside the fact panel. C §2's six-step Connect lifecycle becomes v9370 §2's six-step Connect lifecycle, minus the parts that made it real (C rejects a secret value with the exact sentence "Worlds stores a credential reference, never the secret" and has dirty / pending / validation-on-blur states; v9370 §2 says only "Accept a reference, never a secret"). §11 admits the whole diff: "cabinet bays become a continuous workbench register", "the signature is the labeled seam". A register of labelled stations in a fixed order *is* the cabinet with the doors removed — and v3's anti-repeat list bars round 2's "sentence-first home" and "editorial ledger of facts", which is exactly what a linear register of facts reads as.

**Why it matters.** Rylee chose C's *direction* in round 2, and round 3 exists so six concepts come back from it with different artifacts. If v9370's output is indistinguishable from `direction-C-index.html` with "bay"→"station", the round produced no new information and the differing-paragraph requirement in v3 §"The direction" is satisfied on paper only. The brief also asks for **a brand new design and new api connect layer** (v2, Decisions in force) — "workbench" is a rename.

**Concrete fix.** Change a mechanism, not a noun, in at least three named places, and say which in §11:
1. **Selection replaces the register instead of sitting beside it.** C's bay is chosen from a shelf. Make the register a *work queue* ordered by "needs you → stale → quiet", re-sorting live when the feed changes a state, and make selecting a station push it to the front and expand in place. The queue is a decision surface; a shelf is storage. That is not a cabinet.
2. **Give the seam a function the cabinet never had.** A "narrow labeled seam" is a decoration. Make it the *hand-off channel*: the owner app requests an action through it, Worlds checks the fact's permission and records a receipt, and the seam shows the checked/denied outcome in words. That is design-research pattern 8 (host-mediated action with a permission check) and requirement 5 made visible — and it is the one thing the cabinet's static bezel cannot do.
3. **Break the fixed reading order.** v9370 §2 and C both insist on a fixed shelf order. Let the station own a small local order and let the queue re-sort (see 1); then add one sentence naming what remains fixed (registration order in Settings) and what does not.

## 2. No service ever breaks, and no action has optimistic feedback that settles

**What is wrong.** v3 §"What the real rounds add" 1 requires "an error state (**a service that fails its test or drops off**)" and 4 requires "Actions give **instant optimistic feedback and settle visibly**." v9370 has exactly one error: Notes Sync failing its Connect test (§2, §6). Once a service is connected, nothing ever fails — §5 says only "a modest tick **may** make a service stale", with no rule for which service, when, how a stale service recovers, or how a drop-off is even rendered. Nothing in the document describes an action that reports running → settled. Meanwhile the fixture supplies the material and v9370 ignores it: `studio-printer` (`state: unavailable`, `retry: "Retry last job"`, `allowed: "human"`, `attempts: 1`, `lastError: "job rejected: no media loaded"`), `garden-camera` (`state: unknown`, `source: "none"`, `unknownReason`), `nightly-backup` (`stale`, age 30266s), `local-weather` (`not_configured`, `facts: []`, `emptyReason`). Requirement 2 says at least 3 services; v9370 uses 3, all of them the two C uses plus C's third. Also: §5 says the feed "updates age" but never says to **recompute age from `checkedAt`**, which the fixture's `provenanceFields.ageSeconds` note explicitly requires ("A viewer should recompute age from checkedAt rather than trusting this number"), and never says which views a *tick* updates as opposed to `#simulate-change` (requirement 4 is "one change … updates, at once, the home, that service's own surface, and the agent-facts view" — v9370 only claims that for `#simulate-change`).

**Why it matters.** A daily-use application is judged on what happens when things break; calm structure is only visible when something is failing. This is also the only place the reactive requirement and the honesty requirement meet: optimistic-then-settled is the visible proof that a fact is shared rather than printed. Ignoring `studio-printer` costs the concept its best daily-use surface — a retry that is human-only, shows a real error string, and settles.

**Concrete fix.** Pin the fourth station and the drop-off rule:
- **`studio-printer` is connected at start** (or is the service the live feed drops). Add it to §2's start set. Its station shows `unavailable` in words, the exact `lastError`, and a `Retry last job` button carrying the human-only permission and reason. Clicking it shows **optimistic → running → settle**: the row flips to "retrying…" immediately, then after ~900ms settles to a *second* attempt that succeeds (`printer.status: error` → `healthy`, `printer.last-error-code` → `unknown` with a "no further errors" line — not a blank, per ACCESSIBILITY §1.3). Under `prefers-reduced-motion` the same three steps appear as discrete word changes with no transition. The settle propagates to Home and agent facts in one state update.
- **Scripted drop-off:** on a fixed tick (name the interval and which service), `front-door` or `studio-printer` transitions `live → unavailable`; the station shows a recovery row with the real failure wording, the register re-sorts under it, and a `Re-check` control re-runs the probe optimistically. State the rule for which service and how often; "a modest tick may" is not a decision.
- **`garden-camera` is the `unknown` case** (reached by the scripted drop-off, or available in the station list): every fact renders the word `unknown` and `source: none`, never a blank and never a last-known-good number smuggled in from `checkedAt`. §6 currently promises `unknown` handling but binds it to no service, so it is untestable.
- Say explicitly in §5 that the feed **recomputes `checkedAt`-relative age** (never the stored `ageSeconds`) and that a tick's staleness change updates Home, station and agent facts together, not only `#simulate-change`.

## 3. Memory is a destination with no screen, Settings is two toggles, first run has no way out

**What is wrong.** v3 requires "Real navigation, a **settings screen**, a first-run / empty state". §3 names four persistent destinations; **Memory appears in no other section** — no section says what the Memory view shows, and since Notes Sync's owner app *is* Memory (`app://memory`, §4), a reader cannot tell whether Memory is a Worlds view or just somebody else's app. §3 says Settings "includes live-feed preference and motion comfort" — that is the whole screen, on a product whose day is spent in these four places. First run (§6) is described as a *picture* — "shows no invented readings, a local Worlds/Memory baseline, and a clear Connect invitation" — with no route: nothing says what the Connect invitation does, what Discover lists on a first run, or what the shell shows after the last station is disconnected (the demo can reach zero services only via `#disconnect`, and nothing specifies that state). §1's main gesture promises to "move between its app and the shared facts **without losing your place**" and no section states the mechanism (does selection, scroll position and focus survive a round trip through Connect?).

**Why it matters.** These are exactly the screens a reviewer opens first to decide whether this is "something she would use every day" (Rylee, 2026-10-13). A nav bar with one dead item and a settings screen with two switches reads as a demo harness wearing a product shell. First run is also where "the real application" is decided — it is the first frame anyone sees.

**Concrete fix.**
- **Give Memory a paragraph.** It is the same store filtered: every fact whose owner app is Memory plus `sync.*` rows, with source and freshness as elsewhere, and an empty state of "No notes synced yet — 3 waiting to upload" that deep-links to the Notes Sync station. This costs nothing and it turns requirement 4's "one fact, many places" into three live views instead of two.
- **Make Settings a screen with four rows**, each with stated scope and effect: live feed on/off **and interval**, motion comfort (with what it removes, named), "What the agent may see" — every fact with its agent permission and the exact fixture reason, including the `frontdoor.guest-code-used` denial — and a data notice carrying the MOCKUP statement plus a "start over" that returns to first run.
- **Make first run a route, not a state.** One sentence each: the CTA enters Discover (which lists Notes Sync, Studio Printer, Local Weather by fixture id/name/state, nothing invented); after Publish the person lands on the new station; if the last station is disconnected, Home shows the same invitation with the shell and Memory intact, and history retention stays UNKNOWN as §10 says.
- **Pin "without losing your place"**: selection, scroll offset and focus target are restored on Back from a station and on return from Connect; the mobile sheet (§4) closes to the same row.

## 4. Two widths, one layout — the phone is the desktop, reflowed

**What is wrong.** v3 requires "**Two first-class layouts, not one stretched** … mobile … is not a squeezed desktop." §12 gives 1440px as rail (224) + register (~300) + workspace, and 390px as "the four-item bottom navigation, a single-column Home register, then a dedicated service detail … place the owner app first and facts immediately after". That is one layout with a different nav bar: same regions, same order, same content, reflowed to a column. Two specific symptoms: (a) at 1440 a ~300px register column holding three services is mostly empty chrome, and it is the cabinet's shelf again (see gap 1); (b) at 390 the facts surface dumps *every* row — value, source, freshness, agent/human/who-can-act — directly under the app frame, which is the desktop facts panel in a narrower box, not a phone information design. §4 compounds it by leaving the desktop app/facts relationship as "beside **or** above" — unspecified is not a layout.

**Why it matters.** The layouts are two of the four things this round actually added, and one of them is currently an afterthought. It also costs the signature: a "seam" that is a 1px divider on desktop and a gap on mobile is not an element.

**Concrete fix.**
- **1440:** selection *replaces* the register (per gap 1), so the workspace is wide. Fix the seam as a real, described joint: app 60% / facts 40%, with a labelled divider carrying owner name on one side and "shared facts — source, checked, who can act" on the other. If a register must persist, make it a ~64px strip of state-worded chips, not a 300px list of three names.
- **390:** give the station its own density. Title + state word + owner summary; the owner app in its bounded frame; a **compact facts strip** of two or three rows showing only label, value and state word; then a "Show all facts" disclosure that expands the full rows with source, freshness and the three permission fields; then the action row (`#disconnect`, `#simulate-change`, `#live-toggle`) in a sticky bar above the bottom nav. Two densities, not one density in a narrower box.
- State the mobile reading order explicitly as a numbered list in §12, and say which desktop affordances are dropped on purpose (and which are not merely reflowed).

## 5. The design system is used as a list of refusals, and the whole warmth budget is one sprout

**What is wrong.** §8 says the skill's "patterns do not govern dense product UI", and skeuomorphism is admitted only as what it is *not* — "one flat, labeled work surface and a tiny inline SVG sprout, not textured panels or pressable fake hardware". Every sentence in §8 is a disclaimer; there is no craft decision the system *produced*. v2 (Prompt guidance, lever 1) says "Bind to a design system … do not invent values outside it", and §8 then invents one: "a soft, low-glare neutral field" is not a `ds-skeumorphism` token (`Surface: #FFFFFF`, `Neutral: #FFFFFF`). The type families (`Roboto`, `Germania One`, `JetBrains Mono`) and weights are dropped without a word; the spacing and type *scales* survive. The dials in §1 (variance 5, motion 2, density 4) are asserted, not derived from the skill's dial-inference step as the skill asks. Separately, §6's entire whimsy budget is one inline SVG sprout shown once, after a successful connection, plus one sentence of kind copy — while v3 asks for "kind micro-copy, a tiny illustration or character accent … a gentle motion on a state change, a satisfying 'connected' moment", and the decision in force is "whimsy and warmth laced in". One sprout at one moment is not "laced in"; it is a single ornament on an otherwise flat sheet. (Both this concept and C are filed under `skill-taste-skill` + `ds-skeumorphism`; if v9370's assigned pair is different, §8 is simply wrong and must be corrected to the assignment.)

**Why it matters.** Craft rules are followed when a system changes a decision, and this DESIGN.md shows no decision it changed. And the warmth failure is downstream: if you use the skeuomorphic system only as an exclusion list, there is no physical, human, tactile material available — so warmth can only be pasted on as one icon, which is the "theme park by ornament" failure the decision in force warns against in the other direction.

**Concrete fix.**
- **Bind positively.** Name the tokens used and the substitutions made, in a table or a short list: `#FA3C00` used only as a non-text marker after a contrast check, `#111827` text, the 4/8/12/16/24/32 spacing and 12/14/16/20/24/32 type scales applied, `#FFFFFF` confined to small frame interiors, and the local-first substitutes for Roboto / Germania One / JetBrains Mono (system stack; state it as a substitution required by the no-external-fonts floor, not as a preference). Replace "a soft, low-glare neutral field" with the actual token used and why it satisfies ACCESSIBILITY §1.6.
- **Use skeuomorphism for the one thing it is genuinely good at** — a physical indicator you can read without colour — and make it the warmth carrier. Each station gets a small engraved **state plate**: the state *word* set into a plate whose edge treatment changes with the state (flat / hairline / inset), so the plate reads at a glance and the word carries the truth. `#simulate-change` then has somewhere to go: the Front Door plate physically settles from "Needs a human" to "Healthy" in one 150–250ms move per the system's own motion tokens, the sprout settles into the plate, and under `prefers-reduced-motion` the plate changes with no travel. That is warmth *and* an accessibility win in one element, instead of an ornament beside the truth.
- **Spread the moments.** §6 should list at least three more small ones with their exact trigger and copy: a settling ack after Publish ("All set; Notes Sync has a place here." is already the best line in the document — keep it), a quiet inline hint on the disabled `visitor-3` row ("the agent can't see this one"), a hand-checked first-load line, and one hand-drawn-as-inline-SVG station glyph per service that means nothing on its own (status is always in words). All at zero cost to the structure.
- **Derive the dials** with the skill's inference step (one line: what the design read is, and why motion lands at 2 rather than the 6 baseline) rather than asserting them.
