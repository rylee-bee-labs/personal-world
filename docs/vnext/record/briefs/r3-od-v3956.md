## DESIGN.md

# v3956 · The service commonplace

**Design read:** A daily-use personal service shell for one person, with a calm, warm voice and a small expressive typographic signature. **Dials:** `DESIGN_VARIANCE 5`, `MOTION_INTENSITY 3`, `VISUAL_DENSITY 4`. This is a product interface; landing-page blocks in the taste skill do not set its structure.

## 1. Metaphor in one line, and the main gesture

Worlds is a commonplace of named service entries: each keeps its owner, published scope, and copied facts together. Main gesture: open the small scope marker on an entry to see exactly which facts Worlds copied, from which source, and when.

## 2. Integration model: how a service plugs in, where it lives in the shell, how its facts flow

Start with Media Shelf (`healthy`) and Front Door (`needs_attention`); show Nightly Backup (`stale`) in the register so the starting shell covers three fixture services. Every fixture service remains an independent owner; Connect entries, Home summaries, selected-service detail, Memory's Agent facts register, and Settings read one in-memory store keyed by fixture fact ID. `#add-service` runs six real button steps for Notes Sync: Discover → Credential reference → Safe test → Preview → Choose what to publish → Publish. Accept a credential reference only, never a secret; explicitly show test running, success or failure, and recovery without suggesting a provider call occurred. Preview the fixture's `sync.provider-reachable`, `sync.local-pending`, and `sync.last-synced`; publication checkboxes select a persistent, visible scope set. Only checked fixture facts appear in Worlds' shared surfaces.

The commonplace differs from a bay or dock: the register stays the primary object, and opening a service's scope marker is the central interaction. One provenance line is identical in the register row, service detail, and Memory for each published fact: `Copied from {source}, checked {checkedAt}`. An open scope marker lists the chosen fact IDs, labels, sources, and checked times. `#simulate-change` applies the fixture `crossViewExample` to `frontdoor.back-door` in the same store update, so Home's attention count, Front Door, and Memory's Agent facts row agree without reload. This is a mock handoff/review; Worlds never locks the door.

Actions have three visible phases. Immediately on `#simulate-change`, the value reads `locked · pending mock review` and Home's attention count changes to `0`; after 700 ms the pending label resolves to `Mock review complete` with an explanatory note. A deterministic failure case is available on the next simulated change: after the same optimistic update, at 700 ms it reverts all three views atomically, displays `Mock review did not complete; the fixture change was not retained. Try the mock change again.` and `Last attempted: 0s ago` (then age that text); retry uses the same button. No external action occurs in either branch. All changes remain visibly MOCKUP data.

## 3. Navigation between Worlds and a service (phone and desktop)

The persistent destinations are Home, Connect, Memory, Settings. Home is the attention summary and cross-service view; Connect is the named service register and selected entry; Memory contains durable-state entry points and the **Agent facts** sub-view; Settings holds only fixture-supported connection, feed, and boundary details. Selecting a service on desktop leaves the register visible beside its detail. At 390px, Connect has a register screen and a separate selected-service detail screen with an explicit Back button; the four shell destinations remain a dedicated bottom navigation. Keyboard order is skip link, navigation, main, then complementary facts, with visible focus, semantic headings, and targets at least 44px. In narrow view, the screen's source order is register, selected detail, facts; Back restores focus to the invoking service control.

Memory's Agent facts sub-view is a filterable register over the same published records, showing source, observed/checked time, freshness, and separate agent/human visibility and action permissions. It has a persistent `role="status"` live-region container. With zero published facts it says `No facts are published to Worlds yet` and links to Connect; no placeholder facts appear. Settings lists connected services with a per-service Disconnect control, credential reference label and submitted time (never a secret), live-feed interval and pause/resume, and the MOCKUP note that embedding isolation is unverified. It invents no theme, account, or provider settings unsupported by the fixture.

## 4. The embedded-app frame (sandbox, fallback, what the shell keeps around it)

The selected owner's app is a bounded embedded frame beside the scope/fact view at desktop, and before facts on mobile. Keep service name, exact state word, Worlds navigation, and a visible owner fallback outside the frame. Fixture fallbacks shown: Media Shelf — “Open Media app” (`app://media`); Front Door — “Open Home app” (`app://home`); Garden Camera — “Open Home cameras” (`app://home/cameras`); Nightly Backup — “Open Backup settings” (`app://settings/backups`); Notes Sync — “Open Memory app” (`app://memory`). Also preserve the fixture fallbacks when Studio Printer or Local Weather is selected: “Open Studio printers” (`app://studio/printers`) and “Open provider settings” (`app://settings/providers`). If embedding fails, explain the owning app remains available and keep its link. The mock frame receives no Worlds credential. Actual browser isolation, sandbox flags, and app messaging are UNKNOWN. Approvals hand off to Project Home; other actions hand off to the owning app.

## 7. Borrowed from Homarr / Dashy / HA cards / MCP ext-apps, and what is deliberately different

Borrow Homarr's one integration feeding multiple surfaces, Dashy's in-place app opening, Home Assistant cards' shared state, and MCP ext-apps' contained UI boundary. Deliberately use a provenance register, where one identical copied-from line can be compared across Home, service detail, and Memory, with publication scope opened at the entry itself. The interaction is to inspect what Worlds copied and where it came from, not to open a bay or dock two panels as C does.

## 11. How it differs from C, and what it keeps

Unlike C's fixed cabinet bays and docked app/fact pair, this concept keeps a continuously visible register as the primary surface and makes the published-scope disclosure the core interaction: opening it audits a chosen set of copied facts and their provenance. The matching `Copied from …, checked …` line across Home, service detail, and Memory makes agreement inspectable in a way C's selected-bay pairing does not. It keeps C's real Home / Connect / Memory / Settings shell, explicit ownership, exact status words, persistent owner fallbacks, honest unknowns, and the rule that Worlds composes facts while owners retain actions and authority.

## 12. Desktop and mobile layouts; live feed and checker controls

**Desktop, 1440px:** persistent left rail with Home, Connect, Memory, Settings; main area has the service register and selected detail; the bounded owner app and Worlds-owned facts sit side by side inside detail. The first screen shows `#add-service`, `#simulate-change`, `#live-toggle`, and selected-service `#disconnect` without opening a menu. Memory exposes its Agent facts sub-view in its own destination. **Mobile, 390px:** dedicated four-item bottom navigation with safe-area padding; Connect register and selected detail are separate single-column screens, with visible Back on detail; detail order is service header, app frame, scope/facts, owner fallback. Home and Memory use one-column reading order. The same four controls are visible or one ordinary scroll away, never behind horizontal scrolling; targets remain at least 44px. **At 768px**, navigation becomes a compact top row and app precedes facts in a single column. DOM order follows skip-link, navigation, main, complementary facts; CSS does not reorder reading sequence.

`#live-toggle` is visibly labeled Pause live feed / Resume live feed; feed is ON by default and a tick occurs every 5 seconds. Each tick advances displayed freshness age in seconds from its fixed fixture `checkedAt` timestamp (never moving the source timestamp forward without a fixture event), and updates every rendered view without reload; age refresh is not announced. On every twelfth tick while unpaused, Notes Sync's service state changes to `stale`, `sync.provider-reachable` remains `unavailable`, and its two other fixture facts retain their own states; the UI says this is a simulated feed change. On the next live tick, Notes Sync returns to its fixture baseline `unavailable`; the stale interval is therefore five seconds. Pause freezes both data and motion; resume continues the tick sequence. `prefers-reduced-motion` removes transitions and animation but never pauses data ticks. For a meaningful transition, update the pre-existing polite live region with one concise batched message; routine age updates stay silent. Checker contract: `#add-service` is the Connect lifecycle trigger; `#disconnect` is visible on the first screen for the selected service and opens a confirmation with a button labeled “Disconnect”; `#simulate-change` updates Home, service detail, and Memory's Agent facts together; `#live-toggle` controls the default-on feed; a visible MOCKUP label remains present on every screen.
