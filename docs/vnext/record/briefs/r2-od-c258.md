## DESIGN.md

# c258 — Service stage

## 1. Metaphor in one line, and the main gesture.
Worlds is a service stage with a fixed, equal-weight register: each service keeps its own work area inside a persistent shell. The main gesture is **open a service room from the register, then return to the same shared home**. This is shell-route navigation, not a camera or scene change.

## 2. Integration model: how a service plugs in, where it lives in the shell, how its facts flow.
The first render has exactly two connected fixture services: `garden-camera` (Garden Camera, `unknown`) and `front-door` (Front Door, `needs_attention`). `#add-service` starts the third-service Connect flow for `studio-printer` (Studio Printer, `unavailable`). Render six actual steps: (1) Discover lists Studio Printer and its owner; (2) Credential reference has a labelled reference field, refuses a secret value with the explanation “Enter a reference to a credential; Worlds never accepts the secret itself,” and shows dirty/submitted-pending/error states; (3) Safe test has Run, running, passed and failed states with recovery; (4) Preview lists `printer.status` (`unavailable`), `printer.queue` (1 job), and `printer.last-error-code` (`E-MEDIA-02`) plus the offered human retry capability; (5) Choose to publish uses explicit checkboxes for those three facts and a summary before saving; (6) Publish adds the service bay and its selected fact IDs to all shared views. Do not display a secret or make a real connection.

All three service bays have the same width, order treatment, and depth. State text, not size, position, or perspective, carries attention. Home, each service room, and Agent facts render from one in-memory record keyed by fixture fact ID. `#simulate-change` applies fixture `crossViewExample` action `lock-back-door` to `frontdoor.back-door`: show `locked`, `front-door.state: healthy`, and `attentionCount: 0` in the Front Door room, Home composition, and Agent facts in one state update. This is a mock review/handoff demonstration; it does not operate a lock. `#disconnect` confirms the selected service name, removes its bay and embedded frame, and leaves other services and shell routes working.

## 3. Navigation between Worlds and a service (phone and desktop).
The shell header and navigation for Home, Connect, Memory, and Settings stay mounted. Desktop keeps an equal-cell service register beside a selected room pane; selecting a service changes the shell route and pane content. At 390px the register becomes a vertical list and the room occupies the page beneath persistent shell navigation with Back to Home. Focus enters the room heading and returns to its invoking service control. Semantic order is navigation, main, then complementary Agent facts; all controls are keyboard reachable, visibly focused, and at least 44px.

## 4. The embedded-app frame (sandbox, fallback, what the shell keeps around it).
The selected service's own UI sits in a bounded room frame. The Worlds header, service name/state, Back, and owner fallback remain outside the embedded content and visible while it is open. Keep the fallback available inside the frame edge at all times: Garden Camera — “Open Home cameras” (`app://home/cameras`); Front Door — “Open Home app” (`app://home`); Studio Printer — “Open Studio printers” (`app://studio/printers`). Fixture links use `app://` only. Embed sandbox attributes, origin policy, and app-to-shell messaging are UNKNOWN; no Worlds credential is passed by design. If embedding is unavailable, show the owner link and a plain explanation. Worlds renders no service command inside its shell.

## 5. The agent/human shared-facts model (source, freshness, who sees, who acts).
Agent facts is a view over the same records, not a copy. Every fact shows source, observed/checked time, freshness in words, and separate Agent can see / Human can see / Who can act fields. For `frontdoor.back-door`, agent is `read`, human is `act`; show the fixture reason verbatim: “Locking the door changes the external system and is the person's decision.” For `frontdoor.guest-code-used`, human is `read`; agent is `none`, shown as a named, disabled, focusable control with reason verbatim: “Identifying a person is human-only in this fixture; the agent sees that a guest code was used, not who.” `frontdoor.unlocked-for` is `read` for both. The `lock-back-door` mock handoff routes approval to Project Home; non-approval service actions route to their owning app. Studio Printer's retry is human-only and is an owning-app handoff, not an approval.

## 6. States: empty/first run (zero services, zero providers), quiet, needs-you, stale, unknown, disconnected.
Zero services shows “Connect a service,” explains that Worlds and local Memory still work, and shows no provider readings. Zero providers adds no placeholder services or values. Quiet is the post-demo state after the mock Front Door update: `attentionCount: 0` and no needs-you item, while Garden Camera remains unknown and Studio Printer remains unavailable. Needs-you before that change is Front Door's exact `needs_attention` state and `attentionReason`. Unknown Garden Camera shows `unknownReason` and “no current observation”; no frame value is inferred. Studio Printer keeps `printer.queue` live and `printer.last-error-code` live while `printer.status` is unavailable. Disconnect names the removed service and leaves the other routes usable; retained history is UNKNOWN. Loading, failed test, empty preview, and long content each have explicit explanation/recovery; no persistent animation. Reduced motion removes route travel.

## 7. Borrowed from Homarr / Dashy / HA cards / MCP ext-apps, and what is deliberately different.
Borrow Homarr's reuse of one integration across UI and assistant, Dashy's in-place owner-app opening, Home Assistant's explicit state labels, and MCP ext-apps' contained UI/host boundary. Deliberately, no freeform map, route graph, cable, or spatial status encoding: the stage is an equal service register embedded in a real persistent Worlds shell, not an operational topology.

## 8. Your OpenDesign starting point (skill + design system) and how you used it; which guide rules you applied.
Starting point: `swiss-creative-mode-template` and `ds-perspective`. Borrow only the template's grid, type scale, and hotspot/disclosure discipline; discard its video/deck scenes, slide navigation, theme switching, and palette cycling. Shell routes and the mounted header/status remain persistent around the service frame. Keep Perspective's 4/8/12/16/24/32 spacing and 12/14/16/20/24/32 type scale. Use `#111827` text, `#00BD7D` as a small non-text primary accent, and `#D97706` / `#DC2626` only with explicit warning/danger labels. The `#FFFFFF` surface token is restricted to small inset areas; large surfaces use a dark-text neutral only if sourced from the browser/system canvas, with no invented color token. Primary buttons use dark text on a neutral surface; green is not small-text foreground. Check text at 4.5:1, large text and UI boundaries at 3:1, and focus at 3:1 against adjacent colors before prototype review; if green fails, it loses text and fill roles and remains a non-text marker. Follow no pure-white large surfaces, no neon, static loading, explicit states, 44px targets, 390px no-scroll layout, visible focus, reduced motion, keyboard parity, and MOCKUP label.

## 9. Signature element, hero thesis, reference lock.
Signature: one service room opens inside a persistent Worlds shell while the equal register, owner identity, status, and shared-fact view remain present. Hero thesis: “Independent services share a home without sharing authority.” Reference lock: Finder's stable sidebar-to-content navigation and Home Assistant's explicit entity-state presentation; borrow only those mechanics.

## 10. Risks and UNKNOWNs.
Real embed capability and browser-enforced sandbox details, service protocol, actual Connect API, and disconnect-history policy are UNKNOWN. Fixture timestamps and values are synthetic, not live readings. Contrast combinations must be measured in the prototype; no token may be weakened to preserve the accent. This design specifies a mock interaction, not a verified service connection.

- **Start state / third service:** pinned two starting services and Studio Printer as the third, including all six rendered Connect states and exact offered fact IDs/values.
- **Fallback:** used every composed service's fixture label and `app://` href verbatim; only actual embed mechanics remain UNKNOWN.
- **Unearned spatial hierarchy:** all service cells are equal size and depth; state words carry hierarchy.
- **Deck-template skeleton / deferred tokens:** retained only grid/type/disclosure craft, replaced scene navigation with persistent shell routes, and fixed the Perspective token roles and contrast decision above.
