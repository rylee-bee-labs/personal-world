## Your DESIGN.md

# v4220 — Service folio

**MOCKUP direction; no prototype or reading is approved.** Worlds is the frame around independent services, not their replacement.

## 1. Metaphor in one line, and the main gesture.
Worlds is a service folio: each service has a clearly named page, while its shared facts travel as small, source-stamped slips. The main gesture is to open a service page, see its own app beside the facts Worlds shares, and choose a clear next step.

## 2. Integration model: how a service plugs in, where it lives in the shell, how its facts flow.
Start with Media Shelf (`healthy`) and Front Door (`needs_attention`); present Nightly Backup (`stale`) as the third composed service, using fixture IDs, names, states, and facts verbatim. `#add-service` begins Notes Sync (`unavailable`) in six named stages: discover; enter a credential reference only (never a secret); run a safe test; inspect preview; choose facts to publish; publish. Preview keeps `sync.provider-reachable` (`unavailable`), `sync.local-pending` (3 notes, `live`), and `sync.last-synced` (`stale`) distinct. Each service owns its app and actions; Worlds composes selected facts in Home and Agent facts. `#simulate-change` applies the fixture's `lock-back-door` example to `frontdoor.back-door`, updates Front Door to `healthy` and Home attention count to 0, and refreshes the Agent facts row in the same store update. It is mock review/handoff only; Worlds does not lock the door.

## 3. Navigation between Worlds and a service (phone and desktop).
Persistent Home / Connect / Memory / Settings navigation frames every view. Desktop keeps the navigation rail visible; a readable service index opens a two-column service page with the owning app and shared fact slip side by side. Mobile uses a bottom navigation bar and single-column pages: service index, then selected service detail, with a visible Back control. The first Connect screen shows `#disconnect` for the selected service without opening another panel. Preserve semantic source order, keyboard access, visible focus, and 44px targets.

## 4. The embedded-app frame (sandbox, fallback, what the shell keeps around it).
The service page contains a bounded, labeled app frame with owner name and a visible fixture fallback: “Open Media app” (`app://media`), “Open Home app” (`app://home`), or “Open Memory app” (`app://memory`). Worlds navigation, back, service state, and shared facts remain outside and around the frame. If embedding fails, explain that state and keep the owner link and facts available. The mock frame receives no Worlds credential; actual browser isolation, sandbox flags, and app messaging are UNKNOWN. Approval handoff goes to Project Home; other actions go to their owning app.

## 5. The agent/human shared-facts model (source, freshness, who sees, who acts).
The same fact record feeds Home, the service page, and Agent facts. Every row gives fact label/value, source, observed or checked time, explicit freshness/state, and separate agent/human visibility and action permissions. Render `none` as a named disabled control with its fixture reason, never hide it. For `frontdoor.back-door`, the agent reads and the human acts: “Locking the door changes the external system and is the person's decision.” For `frontdoor.guest-code-used`, the agent's disabled permission explains: “Identifying a person is human-only in this fixture; the agent sees that a guest code was used, not who.” Facts retain their independent states; a failed provider does not erase locally available data.

## 6. States: empty/first run (zero services, zero providers), quiet, needs-you, stale, unknown, disconnected.
Zero services offers Connect and a useful local Worlds/Memory baseline; zero providers shows no invented readings. Quiet is Media Shelf's `healthy`. Needs-you uses Front Door's exact state and fixture reason. Nightly Backup stays `stale`; unknown is stated in words with its reason, never inferred as healthy. Disconnect names the service and requires confirmation with a button labeled “Disconnect”; after removal, say plainly what is gone while other destinations remain usable. Include a failed service-test state with recovery and an embedding-unavailable fallback. `#live-toggle` starts ON and pauses/resumes fixture freshness ticks; stale transitions update every view together. Motion is restrained, one-shot, and removed under `prefers-reduced-motion`; data updates continue. No status relies on color alone.

## 7. Borrowed from Homarr / Dashy / HA cards / MCP ext-apps, and what is deliberately different.
Borrow Homarr's shared integration feeding several views, Dashy's named service checks, Home Assistant's explicit stale/unknown states, and MCP ext-apps' contained UI boundary. As the research note flags these mechanics as memory-based rather than live-verified, treat them as pattern references, not claims about current products. This folio keeps the service's owning app visible beside its shared facts and puts person-readable provenance ahead of provider-shaped controls.

## 8. Your OpenDesign starting point (skill + design system) and how you used it; which guide rules you applied.
Starting point: `skill-minimalist-skill.md` + `ds-pinterest.md`. Carry forward warm sand neutrals, plum-black text, generous but purposeful page spacing, and rounded folio sheets; use no Pinterest brand red, external imagery, or invented font asset. Type uses an intentional system sans stack with fallback, clear hierarchy, and 15–18px body copy. A single hand-drawn inline SVG bookmark/tab marks the current service; it is decorative and hidden from assistive technology. Apply the craft guides: one signature move, named tokens and restrained accent, no gradients/emoji/filler/invented metrics, explicit state coverage, 4.5:1 body and 3:1 large/control contrast, keyboard-visible focus, reduced-motion support, and calm optimistic feedback. Label every view MOCKUP.

## 9. Signature element, hero thesis, reference lock.
Signature: a small “fact slip” that appears unchanged on Home, beside its owner app, and in Agent facts; its source and freshness remain attached wherever it appears. Hero thesis: “A service keeps its own page. A fact keeps its source.” Reference lock: Notion's document-like hierarchy and Apple Home's service-to-state relationship; borrow mechanics only, not their palettes or skins.

## 10. Risks and UNKNOWNs.
Connect protocol details, actual credential-reference handling, browser-enforced embedding isolation, service messaging, and disconnect history are UNKNOWN. The live feed is a synthetic mock, not a real reading. The stationery metaphor must not imply that facts are manually authored or detached from their owners. Contrast needs implementation checking.

## 11. How it differs from C, and what it keeps
C's fixed service cabinet pairs each owner bay with a docked app and fact card. The folio keeps C's real Home / Connect / Memory / Settings shell, independent service ownership, honest states, owner fallback, and shared human/agent facts, but makes the portable fact record—not a cabinet bay—the signature. Service pages read as warm editorial documents, with the same fact slip reused across views; there are no cabinet compartments, physical bezel, or simulated hardware.

## 12. Desktop and mobile layouts
At 1440px, keep the four destinations in a persistent left rail, the service index in a narrow middle column, and the selected service's embedded app beside a fact column in the main canvas. The full first-screen Connect surface shows the selected service and `#disconnect`; keep `#add-service`, `#simulate-change`, and `#live-toggle` plainly visible. At 390px, use a persistent four-item bottom bar and a single-column reading order: service heading/state, owner app frame and fallback, shared facts, then actions. The index and detail are separate screens with an explicit Back button; no sideways scrolling. Keep all controls at least 44px, allow text reflow at 200% zoom, and preserve the same state and actions without relying on desktop hover or motion.

# Critique — v4220 "Service folio" (round 3)

Critique of `docs/vnext/round3/v4220/DESIGN.md` against `concept-brief-v3.md` (which carries `concept-brief-v2.md` forward), `direction-C-DESIGN.md`, and `fixture.json`. ## 1. The shell has four named destinations and one designed screen. Settings, Memory, and Agent facts have no layout, and Agent facts is not reachable by navigation.

**What is missing or wrong.** Brief v3, "the real rounds" item 1: *"A real application, something she would use every day. Real navigation, a settings screen, a first-run / empty state…"* The DESIGN names Home / Connect / Memory / Settings as persistent navigation (§3) and then never designs Memory or Settings. Settings appears only as *somebody else's* owning app (`app://settings/backups` for Nightly Backup, §4). §6 gets one clause — "a useful local Worlds/Memory baseline" — for first run, which is a promise, not a screen. Worse, §2 and §5 build a whole third surface, the **Agent facts** view, which is in no navigation list and appears in no layout: "The same fact record feeds Home, the service page, and Agent facts" (§5). Requirement 4 in brief v2 needs the agent-facts view to update "at once" with Home and the service surface — if it is not in the nav, it is not a view a daily user can open, and the checker/user cannot see that the three surfaces moved together. There is also a contract risk: §3 and §12 place `#disconnect` on "the first Connect screen", while brief v3's checker contract says `#disconnect` is *"visible on the first screen for the currently selected service (not hidden until something is opened)"*. A first-paint reading of that clause is Home, not Connect.

**Why it matters.** This is the difference between an application and a page with three tabs — the exact round-1 failure the owner named ("concepts on a page"). The person who uses Worlds every day will open Settings once (to change what is published, to check what a credential reference points at, to see what a disconnect took away) and will open Agent facts when they ask "what can my agent see and do, and how fresh is it?" That second screen is the concept's whole thesis about shared human/agent facts, and it is currently unreachable.

**Concrete fix.**
- Give Settings a designed screen at both widths, containing: published-facts toggles per service (the same data as Connect step 5, editable later), credential-reference rows showing *reference name only* with the fixture sentence "Worlds stores a credential reference, never the secret", live-feed controls (interval + the `#live-toggle` state), a motion/reduced-motion acknowledgement line, and a plain list of disconnected services with what was removed (this also closes brief v2 req 6's "says plainly what is gone" beyond the toast).
- Give Memory a designed screen: the local baseline only — locally-sourced facts (`sync.local-pending` 3 notes, `frontdoor.unlocked-for` 47 minutes, `media.items` 1284) and an explicit line that nothing here is a provider reading. This is where "zero providers shows no invented readings" (§6) actually gets drawn.
- Put Agent facts in the nav. Either make it a fifth destination, or (better for a 390px bottom bar, which §12 caps at four items) make it a labelled section *inside* Memory titled "Agent facts", and say so in §3, §5 and §12 so the three-view update in req 4 is demonstrable by clicking.
- State which screen is the app's first paint after load, and put `#disconnect` for the selected service on *that* screen, with the Connect-surface copy as the secondary placement. One sentence in §3 removes the ambiguity.

## 2. The reactive layer has no tick, no stale event, no optimistic settle, and pause can freeze the freshness text into a lie.

**What is missing or wrong.** Brief v3 item 4: *"A simulated live feed from the fixture: a gentle tick (every few seconds) … that changes freshness ('checked 2s ago' → '12s ago'), occasionally moves a service to stale, and updates every view that shows it without a reload. Actions give instant optimistic feedback and settle visibly. Transitions between states are visible (and calm under reduced motion)."* The DESIGN supplies one sentence (§6: "`#live-toggle` starts ON and pauses/resumes fixture freshness ticks; stale transitions update every view together") and no mechanics: no tick interval, no rule for how `checkedAt` becomes an age string, no named service that goes stale, no visible pending→settled sequence for any action, no specified transition. The only action in the concept, `#simulate-change`, is instant because it is a mock, so "optimistic feedback and settle visibly" is designed zero times. Pause is worse than undesigned: if ticking stops and the age string is frozen in place, every fact on screen silently becomes a stale reading wearing a live label — a direct hit on brief v2's floor "nothing presented as a real reading" and on brief v3's "stale and unknown said in words". §6 also says the tick "pauses/resumes freshness ticks" while §2 promises fixture states used "verbatim"; nothing says how a *periodic* transition out of `live` is reconciled with the fixture's own rule that *"Concepts must not mutate the fixture"* (`crossViewExample._comment`). The honest mechanism exists and the DESIGN does not use it.

**Why it matters.** Reactivity is one of the two decisions the owner just made in force ("are reactive <3") and the thing round 2 was told round 1 lacked (owner feedback on #322: "genuinely reactive UI"). As written, the reader cannot tell whether this concept has a live feed or a `setInterval` that bumps a number. A build from this document would ship a counter, and the freshness/provenance claim that the signature rests on ("its source and freshness remain attached wherever it appears", §9) would be the one thing that is not actually live.

**Concrete fix.** Pin all of it in §6, in these terms:
- **Tick:** 3 s. Each tick recomputes age from `checkedAt` against a mock clock — the fixture's own `provenanceFields` note says the viewer must not trust `ageSeconds`. Age strings render as words ("checked 12s ago"), recomputed, never stored.
- **The stale event:** do not overwrite a fixture fact. Name the drop-off explicitly as a simulated provider check: on tick N (say tick 6, ~18 s in), Media Shelf's freshness source changes `local` → `none` and its freshness state word follows the fixture vocabulary to `stale`, with the fixture's own summary style of copy — "Media Shelf has not answered since 14:24:26. The last answer is still shown." The *last known values stay on screen and are labelled stale*; they are not blanked and not restated as current. Home, the service page and Agent facts all change in that one store update. Recovery: the next tick restores it, which also demonstrates the stale→live transition both ways.
- **Optimistic settle on `#simulate-change`:** give it a visible sequence, not an instant jump — the fact slip's value line goes to a pending state ("Locking…") with `aria-busy`, roughly 600 ms, then settles to `locked` with the fixture's `humanReason` shown once under it, while Home's attention count goes 1 → 0 with a settle and `#simulate-change` disables while pending. Under `prefers-reduced-motion` the pending word stays, the animation goes, the data does not.
- **Pause honesty:** on pause, every age string is replaced by the word "paused" with the time it was paused, in every view at once; resume restores ticking and says so. A frozen number must never keep saying "ago".
- **Transition:** one named, 150–200 ms opacity/transform cross-fade on the value line only, per `animation-discipline.md`'s 150 ms convergence and its rule that motion is for state change, not decoration — and removed, not shortened, under reduced motion.

## 3. Whimsy is one decorative, screen-reader-hidden SVG bookmark, and the assigned design system is quoted as adjectives rather than used as a system.

**What is missing or wrong.** Brief v3 item 2 asks for "small, specific, delightful moments: kind micro-copy, a tiny illustration or character accent drawn in inline SVG, a gentle motion on a state change, **a satisfying 'connected' moment**", with warmth in the details and the structure calm. The DESIGN's entire whimsy budget is §8's "a single hand-drawn inline SVG bookmark/tab marks the current service; it is decorative and hidden from assistive technology". The concept's most emotionally loaded moment — publishing a service and getting a connected service — is specified in six words: "publish" (§2). Nothing is said about what the person sees or reads at the instant Notes Sync joins. Section 6's motion rule is a constraint ("restrained, one-shot"), not a designed moment, and the signature (§9, "a fact slip that appears unchanged") is a *consistency* device — it proves the system works; it does not delight anyone.

Section 8 also does not actually use the two assigned sources. `skill-minimalist-skill.md` prescribes a specific system: warm monochrome `#F7F6F3`/`#F9F9F8`, `#EAEAEA` hairline borders, `#111111`/`#2F3437` text with `#787774` secondary, crisp 8/12px radii, a 4/8-based scale, and — directly relevant here — **muted pastel status badges** (`#FDEBEC`/`#E1F3FE`/`#EDF3EC`/`#FBF3DB` with their paired dark text) which are precisely the sanctioned way to give every state a non-colour-coded visual identity without hue-only status. None of that appears. `ds-pinterest.md` prescribes warm olive/sand neutrals (`#e5e5e0`, `#91918c`, `#e0e0d9`), plum black `#211922`, generous radii (16/20/28/40), an 8px base scale, a 12–16px compact type scale, and — as a "Do" — Pinterest Red as the singular bold accent. The DESIGN takes the neutrals, plum black and "rounded folio sheets", then explicitly bans "Pinterest brand red" and does not replace it. The result is a concept with **no accent colour at all** and no named token list, on a design system whose identity is a bold singular accent. C, by contrast, named every value it used (`#111827`, `#FA3C00`, 4/8/12/16/24/32 spacing, 12/14/16/20/24/32 type). And the "15–18px body copy" in §8 is invented: it is neither the minimalist skill's 16px body nor Pinterest's 12–16px compact scale, and it is in tension with §12's own 44px-target mobile bar, which needs a compact scale to stay legible.

**Why it matters.** Two decisions in force depend on it: "whimsy and warmth laced in" and "take into account … the opendesign options". A folio of paper slips is a look, not warmth; the warmth has to be in specific copy and specific moments, and right now the concept has one decorative glyph and no signature interaction moment. Meanwhile an accentless design system means the one visual thing this concept could own — the source-stamped slip — has no way to be recognised at a glance.

**Concrete fix.**
- **Name three warmth moments, with copy, in §8.** (a) The connected moment: on publish, one line in the folio's own voice — "Notes Sync is in. Its provider is not answering yet; your 3 local notes are safe." — plus the slip's source line changing from `checking` to `checked just now`, and one 200 ms settle. That line teaches the exact state model in the concept's own thesis sentence, which is what makes it warmth and not decoration. (b) Kind micro-copy on the state words themselves: the stale Front Door reads "Back door has been unlocked for 47 minutes — longer than usual", not "unhealthy". (c) The bookmark earns its place by being the *only* place a flourish is allowed, and it should not be `aria-hidden` decorative-by-default: give it a text sibling that names the current service, and keep the SVG out of the accessibility tree.
- **Replace the token list.** Write out ~12 named tokens in §8 drawn only from the two assigned sources — canvas `#F7F6F3`, surface `#FFFFFF`/`#F9F9F8`, hairline `#EAEAEA`, plum black `#211922` text, olive `#62625b` secondary, warm silver `#91918c` border/disabled — and pick the state-badge treatment from the minimalist skill's muted pastels (each with its paired dark text, so state is word + tint, never tint alone). Keep the Pinterest radii (16/20/28) for slips and 8/12px for controls, which is where the two systems agree.
- **Decide the accent and defend it.** Either name the muted-pastel set as the entire accent budget with a stated reason (status is the only place colour is allowed, because status is the only semantic), or take a single restrained non-status accent from Pinterest's system and say which one. "No Pinterest brand red" is fine; leaving the accent slot empty is not.
- **Use the assigned type scale** rather than the invented 15–18px: 16px body, 14px caption, 12px metadata/source line (the source line is metadata, and metadata is where Pinterest's compact scale is a gift), 28px section heading at −1.2px. Then reconcile with 44px targets by growing the *hit area*, not the label.

## 4. Requirement 5 is asserted, not shown, and the fixture's own human-only action and honesty cases are left unused.

**What is missing or wrong.** Brief v2 req 5: *"A decision is never made in Worlds; it links/hands off to the owning system (Project Home for approvals, the service itself otherwise)."* The DESIGN states this in §4 and §2 — "Approval handoff goes to Project Home; other actions go to their owning app" — but never specifies a control, a destination, or what the person is told afterwards. §5 treats `human: "act"` as a *permission*, not an action: `frontdoor.back-door` is described by who may act, and `#simulate-change` is described as "mock review/handoff only". So the concept never renders the one thing req 5 asks for — an affordance that hands off.

The fixture hands the concept two things it does not pick up. `notes-sync.retry` is a real human-only action with `label: "Check provider now"`, `allowed: "human"`, `attempts: 2`, `lastError: "provider timed out"` — the cleanest available rendering of "agent cannot, human can, and here is why", on the very service the concept adds through Connect. And two services exist solely to make honesty drawable: `garden-camera` (`state: "unknown"`, `unknownReason: "The device stopped answering at the fixture's baseline; no source has answered since."`, and a fact with `camera.human-detected-today` carrying `agent: "none"` with its own reason) and `local-weather` (`not_configured`, `facts: []`, `emptyReason`). The DESIGN claims it handles unknown (§6: "unknown is stated in words with its reason, never inferred as healthy") while composing **no service that is unknown** — the claim is currently vacuous, and the `emptyReason` service (the zero-fact, zero-provider case) is never on screen.

**Why it matters.** Req 5 is the governance promise the whole agent/human section rests on; without a visible handoff control, §5 is a permissions table rather than a mechanism. And req 1's safe-test failure, §6's "failed service-test state with recovery", and brief v3's error state ("a service that fails its test **or drops off**") all need a real drop-off to point at — which is what `garden-camera` is, in the fixture, with copy already written.

**Concrete fix.**
- **Draw the handoff.** On the `frontdoor.back-door` slip: a named control, "Review in Project Home", styled as a handoff (external-link affordance, 44px), that opens a mock Project Home surface naming the request — "Front Door: back door unlocked for 47 minutes" — with copy stating that nothing was decided in Worlds and that the review is recorded locally afterwards: "Recorded here as reviewed. The door is still unlocked until Project Home changes it." Do not flip `frontdoor.back-door` to `locked` from the handoff; only `#simulate-change` may do that, per `crossViewExample`.
- **Use the retry.** On Notes Sync, after Connect: "Check provider now" (human-only, `attempts: 2`, `lastError: "provider timed out"`), one-shot optimistic state ("Checking the provider…"), settling to the same `unavailable` with `provider timed out` restated, and `sync.local-pending` still `live` at 3 notes. This is the fixture's own warning against collapsing provider failure into local-data failure, and the doc claims to honour it without ever showing it.
- **Add Garden Camera to the composition** (5 services: Media Shelf, Front Door, Nightly Backup, Notes Sync, Garden Camera) so §6's unknown claim becomes a real screen: the `unknown` state word, `unknownReason` verbatim, the last-known frame placeholder that is *not* a frame, and `camera.human-detected-today` rendered as the named disabled control with "The agent may not assert a detection while the source is unknown."
- **Add Local Weather to Connect discover** (it is `not_configured`, zero facts) so the empty-preview and zero-provider states are drawn with `emptyReason` verbatim rather than asserted. If composition must stay at three services, then say explicitly which screen carries `unknownReason` and `emptyReason` — but adding two fixture services costs nothing and closes four states at once.

## 5. The stated difference from C is a change of vocabulary: the 1440 layout, the integration mechanic, and the reference lock are all C's.

**What is missing or wrong.** Brief v3: "Use C as the starting direction, do not clone it." §11 concedes the debt honestly — it "keeps C's real Home / Connect / Memory / Settings shell, independent service ownership, honest states, owner fallback, and shared human/agent facts", i.e. C's facts model, C's states, C's fallback and C's shell — and offers two differences: the metaphor is folio rather than cabinet, and the signature is the fact slip rather than the bay. But compare §12 to C's own §3/§4: persistent left rail with Home/Connect/Memory/Settings, a service index column, and the selected service's **owning app beside a shared fact card** is C's docked inset-plus-fact-card, column for column. The integration mechanic the whole round is about — an owner's app next to the shared facts — is unchanged. So the one structural difference the DESIGN can defend is naming, and the DESIGN half-notices this itself in §10: "the stationery metaphor must not imply that facts are manually authored or detached from their owners" — a warning that its own differentiator is the risky part.

Two further tells. The reference lock (§9) is "Notion's document-like hierarchy and Apple Home's service-to-state relationship" — Apple Home was already half of C's lock ("Apple Home's accessory-to-home state handoff"), and Notion's document hierarchy is the closest available relative of round-2's **"editorial ledger of facts"**, which is on the anti-repeat list. And the folio has no answer to the anti-repeat question it most needs to answer: a warm editorial page with source-stamped rows *is* an editorial ledger of facts. The DESIGN's only defence is the embedded owner app sitting beside the rows — which is C's mechanic. A one-sentence disambiguation from "editorial ledger of facts" is required, and it is absent.

**Why it matters.** The brief's whole purpose in round 3 is to move away from C, not to relabel it. If a reviewer compared 1440px screenshots of v4220 and `direction-C-index.html` and saw the same rail / index / docked-frame-plus-facts arrangement with a paper-coloured background, the round produced one concept, not two — and the "difference from C" paragraph, which is the deliverable that proves independence, would not survive the comparison.

**Concrete fix.**
- **Make the folio structurally different at 1440, not just tonally.** Drop the docked side-by-side and make the folio page a single asymmetric editorial spread: a narrow left margin column carrying *only* provenance (source, checked time, freshness word, who-sees/who-acts), and a wide right reading column carrying label, value, and the owner's app placed *inside the reading flow* at the point where the fact is discussed — with the app's frame edge carrying its owner name as a running head, not a caption. Same data, no dock, no cabinet bay: C pairs app-beside-card; the folio *threads* them through prose order and lets provenance live in the margin. Say this in §11 and §12 with one sentence each. At 390px the margin column collapses above the reading column in source order, which is a real reflow rather than a stack — that also gives the mobile layout its own idea instead of the same order C uses.
- **Change the lock.** Drop Apple Home (C already spent it) and drop Notion. Lock on one editorial system that is about *marginal provenance and specimens* — a naturalist's field-guide specimen label, or a library catalogue card — plus one reference for the fact-slip repetition. Take mechanics only.
- **Add the anti-repeat disambiguation explicitly**, in §11, naming round-2's "editorial ledger of facts": that one is a list of facts with no owning app in frame; this one is an owner's app embedded in the reading order with the facts, so the ledger could be printed from it but the folio cannot lose the app.
- **Say what the folio buys over the cabinet** in one concrete sentence a reviewer can check: the slip is identical on Home, on the service page and in Agent facts, and that identity is what the design is optimising — C's bay is a *location*, the folio's slip is a *portable record*. Then make sure §12 shows the same slip at 1440 and 390 with the same source line, or the thesis is unbuilt.
