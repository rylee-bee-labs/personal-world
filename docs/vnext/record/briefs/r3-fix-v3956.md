## Your DESIGN.md

# v3956 · The service commonplace

**Design read:** A daily-use personal service shell for one person, with a calm, warm voice and a small expressive typographic signature. **Dials:** DESIGN_VARIANCE 5, MOTION_INTENSITY 3, VISUAL_DENSITY 4. This is a product interface, so the taste skill's landing-page blocks do not set its structure.

## 1. Metaphor in one line, and the main gesture.
Worlds is a commonplace book with labeled service entries: open an entry to see the owning app and the facts Worlds can share. Main gesture: select a service name, then move between its app and its shared facts.

## 2. Integration model: how a service plugs in, where it lives in the shell, how its facts flow.
Start with Media Shelf (`healthy`) and Front Door (`needs_attention`); show Nightly Backup (`stale`) in the service register so three fixture services are present. Each entry names its owning app and keeps its own actions there. `#add-service` starts Notes Sync (`unavailable`) through Discover → Credential reference → Safe test → Preview → Choose what to publish → Publish. Accept a reference only, never a secret; show test failure and recovery without pretending a provider call occurred. Publish only checked fixture facts. A single shared in-memory fact store drives Home, the service view, and Agent facts. `#simulate-change` applies the fixture's `frontdoor.back-door` example to all three views together; it is a mock handoff/result, not a Worlds decision or real lock action.

## 3. Navigation between Worlds and a service (phone and desktop).
Persistent shell destinations are Home, Connect, Memory, Settings. Service entries sit within Connect; selecting one opens its detail while shell navigation remains available. On phone, selecting a service replaces the register with its detail and an explicit Back control. Keyboard order follows navigation, main, then complementary facts; focus is visible and all targets are at least 44px.

## 4. The embedded-app frame (sandbox, fallback, what the shell keeps around it).
The selected service's own interface appears in a clearly bounded embedded frame beside its Worlds-owned fact summary on desktop, stacked after it on mobile. Keep service name, state in words, shell navigation, and a visible owner fallback around it. Use the fixture fallback links, including “Open Media app” (`app://media`) and “Open Home app” (`app://home`). If embedding fails, explain that the owning app still works and keep its link available. The mock frame receives no Worlds credential; actual browser isolation and app messaging remain unknown. Approvals hand off to Project Home; other actions hand off to the owning app.

## 5. The agent/human shared-facts model (source, freshness, who sees, who acts).
Agent facts and human views use the same records, with each fact showing its source, observed/checked time, freshness, and separate Agent and Human permissions. Render `none` as a named disabled control with the fixture reason, never hide it. For `frontdoor.back-door`, the agent can read and the human can act; only the person decides whether to lock it. Routine freshness ticks update labels without announcing every poll. Announce meaningful state changes politely and sparingly.

## 6. States: empty/first run (zero services, zero providers), quiet, needs-you, stale, unknown, disconnected.
First run shows zero connected services and a clear Connect invitation; zero providers means zero readings. Quiet uses Media Shelf's exact `healthy` state. Needs-you preserves Front Door's `needs_attention` label and reason. Nightly Backup remains `stale`; unknown is said explicitly, never inferred as healthy. A failed test names what failed and offers retry or exit. Disconnect confirmation names the service and consequence; after removal, say what is gone while Home, Memory, and remaining entries continue working. Retention after disconnect is unknown. All states include readable text, not color alone. Show a visible MOCKUP label.

## 7. Borrowed from Homarr / Dashy / HA cards / MCP ext-apps, and what is deliberately different.
Borrow Homarr's one integration feeding multiple surfaces, Dashy's in-place app opening, Home Assistant cards' shared state, and MCP ext-apps' contained UI boundary. This concept uses a quiet named-entry register and a paired app/facts reading surface rather than a widget wall or topology; each service's owner remains clear and authoritative.

## 8. Your OpenDesign starting point (skill + design system) and how you used it; which guide rules you applied.
Starting point: `skill-taste-skill.md` and `ds-artistic.md`. Keep Artistic's expressive hierarchy and Limelight display face for short headings, but its high-saturation blue, pure-white broad surfaces, and high-motion defaults conflict with Worlds' comfort floor. Use its 4/8/12/16/24/32 spacing, 12/14/16/18/24/30/36 type scale, `#111827` text, and a small `#3B82F6` primary action accent only where contrast and low-glare checks pass; no secondary purple. Favor a soft neutral surface rather than large pure-white panels. Keep one radius system and one accent. Apply the skill's anti-default and copy self-audit guidance; use a self-contained HTML/CSS/vanilla JS prototype with no framework, CDN, external font, or image. Keep loading static, motion purposeful, and honor `prefers-reduced-motion`.

## 9. Signature element, hero thesis, reference lock.
Signature: a narrow, hand-drawn-looking inline SVG page corner that folds around the shared fact summary, marking “Worlds' copy” beside the owning app. Hero thesis: “Every service keeps its place. Every shared fact keeps its source.” Reference lock: Homarr's reactive integration reuse and Dashy's in-place app launch mechanics, not their visual language. Warmth comes from a small “You're all set” connected moment and kind recovery copy, not a character-driven theme.

## 10. Risks and UNKNOWNs.
The fixture is synthetic and every view must remain labeled MOCKUP, never a real reading. Connect protocol details, browser-enforced app isolation, cross-app messaging, and disconnect-history retention are unknown. The inline accent must not imply status or action. Verify text/focus contrast and reflow in the eventual prototype.

## 11. How it differs from C, and what it keeps
Unlike C's fixed cabinet bays and docked inset, this concept treats each service as a named entry in a commonplace register and pairs its app with a folded-corner shared fact note. It keeps C's real Home / Connect / Memory / Settings shell, explicit ownership, honest status words, persistent owner fallback, and the principle that Worlds composes facts while the owning app keeps its actions and authority.

## 12. Desktop and mobile layouts
At 1440px, a persistent left shell rail holds the four destinations; the main column shows the service register and selected service header, with the framed owning app and shared-facts note side by side. Keep `#add-service`, `#simulate-change`, `#live-toggle`, and a visible `#disconnect` for the selected service on the first screen. At 390px, use a dedicated bottom navigation for the four destinations; Home/Connect content becomes a single-column reading order, and a selected service gets its own detail view with Back, app frame, then facts. Keep the same four controls discoverable without horizontal scrolling, reserve safe-area space, and size all targets to at least 44px. A modest 768px layout may collapse the rail to a compact navigation row and stack app before facts. The live feed is on by default, advances fixture freshness/state in one shared store, and has a visible pause/resume control; state transitions are brief and gentle, with no nonessential motion under reduced-motion preference.

## CRITIQUE.md (another engine)

# CRITIQUE — v3956 "The service commonplace"

Reviewed against `concept-brief-v3.md` (with everything in `concept-brief-v2.md` still in force), `reference/direction-C-DESIGN.md`, and `fixture/fixture.json`. Five gaps, most important first.

---

## 1. Two of the four destinations are named and never designed; the agent-facts view has no home

**What is missing.** §3 declares four persistent destinations: Home, Connect, Memory, Settings. Across §1–§12, only Home and Connect ever get content. Memory and Settings appear as nav labels and then vanish: no job, no states, no first-run, no empty, no failure. v3 §1 requires "a settings screen" as part of "a real application, something she would use every day," and this DESIGN.md has none. Worse, §2 and §4 both promise an "Agent facts" view that drives a third consumer of the shared store ("Home, the service view, and Agent facts"), yet no section ever says where that view lives. Requirement 4 in v2 makes it load-bearing: "the agent-facts view shows each fact's source and freshness and, separately, who can see and who can act." A view with no destination cannot be a destination she navigates to daily, and "one fact, many places" is only demonstrable if the third place is reachable by clicking.

**Why it matters.** The daily-use test is decided by the destinations, not the selected-service surface. As written, this concept is a Connect screen with two nav items of scenery. It also quietly dodges v3 §1's "settings screen" clause, which is the single cheapest signal that the author thought about the boring parts of an application.

**Concrete fix.** Add one short paragraph (or table) giving each destination a job, its states, and what it reads from the store. Minimum content: **Memory** hosts the agent-facts view as a filterable register over the same records the service view reads, with the permission rows from §5 and a `role="status"` region; it must state what "zero published facts" looks like, since that is the reachable empty state for a fresh install. **Settings** holds only what the fixture supports, with no invented controls: connected services list with per-service `Disconnect`, the credential *reference* (never the secret) with its label and when it was submitted, the live-feed interval and pause control, and the MOCKUP/boundary note ("embedding isolation is unverified"). Name the agent-facts view explicitly as a sub-view of Memory so requirement 4 has a route.

---

## 2. The permission and state transcription is thinner than the fixture, and three of five owner fallbacks are missing

**What is wrong.** §5 transcribes exactly one fact, `frontdoor.back-door`. The fixture's `permissionVocabulary` rule is explicit: "`none` must render as a named, disabled control with its reason, never hidden." The case that proves it is `frontdoor.guest-code-used` (agent `none`, with the verbatim reason "Identifying a person is human-only in this fixture; the agent sees that a guest code was used, not who"). That row is absent, so §5's "Render `none` as a named disabled control with the fixture reason" is a promise with no instance attached to it. `camera.human-detected-today` carries a second `none` + reason and is also unused. `sync.provider-reachable` (source `external`) and the local/live vs. provider/unavailable split are never mentioned, which loses the exact honesty point that provider failure is not local-data failure.

§6 is thinner still. "Unknown is said explicitly, never inferred as healthy" names no fixture service: Garden Camera (`unknown`, with `unknownReason`) is the one that must render it, and Local Weather (`not_configured`, zero facts, `emptyReason`) is the one that must render a real empty. Neither appears. §4's fallback list has "Open Media app" and "Open Home app" only; the concept's own two other services need **Open Backup settings** (`app://settings/backups`) and **Open Memory app** (`app://memory`). The `retry` affordances (`printer.retry`, `sync.retry`, both `allowed: human` with `attempts` and `lastError`) are never surfaced, so the error-state promise in §6 has no retry object to point at.

**Why it matters.** These are the places where a shell either keeps its promise or quietly invents data. v2's floor and the fixture both demand exact fixture strings; "use its ids, names and states verbatim, add nothing it does not contain" is not satisfied by paraphrasing coverage. C transcribed all three `front-door` rows and both fallbacks; this concept is behind the direction it is meant to differ from.

**Concrete fix.** Add a transcription table to §5 covering every fact the concept publishes: id, label, value, unit, state, `source`, `checkedAt`, agent permission, human permission, and the exact reason string for both `none` rows, plus `frontdoor.unlocked-for` (both `read`). In §6, name the service that carries each state: `healthy` = Media Shelf, `needs_attention` = Front Door with `attentionReason` verbatim, `stale` = Nightly Backup (its three facts are all `stale`, so its register row and its fact rows must not disagree), `unknown` = Garden Camera with `unknownReason`, `not_configured` / zero facts = Local Weather with `emptyReason`. In §4, list all four fallbacks the concept shows. Add the retry line: which services offer one, that `allowed: human` means the control is disabled for the agent with that reason, and that `lastError` is printed as-is.

---

## 3. Reactivity has no optimistic feedback, no settled failure, and no answer about what goes stale

**What is missing.** v3 §4 is specific: "Actions give instant optimistic feedback and settle visibly," the feed "occasionally moves a service to stale," and the checker contract adds that reduced motion governs "animation, not for data." This DESIGN.md answers none of the three. §2 defines `#simulate-change` as "a mock handoff/result," and §12 says the feed "advances fixture freshness/state in one shared store." There is no pending phase, no settling phase, and no description of what a user sees when the mock handoff does not succeed. There is also no scheduled stale event: nothing in §12 says which service drifts, on what trigger, or whether it recovers. And "Routine freshness ticks update labels without announcing every poll" (§5) is right, but "Announce meaningful state changes politely and sparingly" names no live region, so there is nothing to check against `state-coverage.md`'s rule that live-region containers must exist in the DOM before content is injected.

**Why it matters.** "Reactive" is a named requirement with a named checker, and this is the requirement where the concept is thinnest. A tick that only increments an age counter is the minimum reading of "reactive" and it will not read as a live application. And optimistic-then-settle is the exact behaviour that makes a mock action feel like a real one; without it, `#simulate-change` is a button that swaps a value.

**Concrete fix.** In §2 or §12, pin the action triad for `#simulate-change`: (a) optimistic, the fact and the Home count change in the same frame with a pending label; (b) settle, after a stated delay the label resolves and the mock-review note appears; (c) fail, on a declared trigger the value reverts and an inline message states what happened, why, and what to do, with a retry and a "last attempted: Xs ago" line per `state-coverage.md`. Then pin the feed's own schedule: which service becomes `stale` after how many ticks, whether it recovers, and that `#live-toggle` freezes the data as well as the animation. State explicitly that `prefers-reduced-motion` disables transitions but never the tick, and name the polite live region and the three things it announces.

---

## 4. The difference from C is a rename, and the signature repeats a look the anti-repeat list already used

**What is wrong.** §11's stated difference is "C's fixed cabinet bays and docked inset" versus "each service as a named entry in a commonplace register" paired with "a folded-corner shared fact note." Mechanically that is C's layout with different nouns: a register, a selected detail, an app frame beside a shared-fact card, a persistent fallback. Nothing in the interaction differs. Meanwhile the signature itself, "a narrow, hand-drawn-looking inline SVG page corner that folds around the shared fact summary," is the editorial-paper look: the v3 anti-repeat list already burns "editorial ledger of facts" and "hand-drawn triage chart" (both round 2), and the fold/corner device sits on top of round one's `foldout-atlas` (`docs/vnext/round1/foldout-atlas`, the concept C explicitly names as the thing not to re-do). The brief's line is unambiguous: "You may borrow a good mechanism; never the look."

There is also a real requirement being dropped here. Connect step 5 is "choose what to publish," and §2 resolves it with "Publish only checked fixture facts" and then never mentions the choice again. The set the user picked is invisible for the life of the service.

**Why it matters.** v3 §"the direction" requires a paragraph saying how the concept differs from C, and the current paragraph is a vocabulary change. If the folded corner is decoration, the concept is C with a metaphor stapled on and it fails the brief's own anti-repeat test.

**Concrete fix.** Give the corner a job C cannot do: make it the published-scope indicator. It shows how many of the service's fixture facts Worlds chose to publish, folds open to list them with each one's source and `checkedAt`, and is where "Worlds' copy" is stated as a scoped set rather than a label. The gesture is then "open the corner to see exactly what Worlds copied and from where" - a fact-provenance action, not a paper effect. Also add one mechanism C lacks that has nothing to do with paper: a per-entry provenance line ("copied from Media, checked 14:23:58Z") that is the same on the register row, the service surface, and Memory, so the three views can be checked for agreement at a glance.

## 5. The OpenDesign binding contradicts itself and cannot ship as written

**What is wrong.** §8 says Artistic's "high-saturation blue" and "pure-white broad surfaces" conflict with the comfort floor, and then keeps `#3B82F6` as the primary accent anyway. It leaves the surface unpinned - "a soft neutral surface" is a decision deferred, while ds-artistic's Surface and Neutral are both `#FFFFFF` - and it never assigns the status colors the seven states need (`success #16A34A`, `warning #D97706`, `danger #DC2626`) or states what distinguishes `needs_attention` from `stale` from `unavailable` when status is correctly never color-only. One accent plus one surface plus no state tokens is not a bound system.

The buildable problem is the typeface. §8 keeps "Limelight display face for short headings" and also promises "no framework, CDN, external font, or image." Limelight is a Google font; it cannot render in a single self-contained file under that rule. The same applies to ds-artistic's JetBrains Mono. So the concept's only expressive typographic signature is unrenderable in the artifact it is designing.

**Why it matters.** v2's floors say "Bind to a design system (lever 1): each concept has a assigned design system; do not invent values outside it," and "quality comes from decision coverage, not word count." Naming the file and then declining three of its tokens without deciding replacements is not binding. The font conflict means the prototype either silently falls back to Times (killing the stated "small expressive typographic signature" that §1 and §9 both claim is the warmth carrier) or breaks the stack rule.

**Concrete fix.** Pin the tokens: keep `#111827` text, `#3B82F6` as the single accent for action edges only, choose one concrete surface value (and say why it differs from `#FFFFFF`), and reserve success/warning/danger strictly as non-text marks while naming the state word as the sole status channel, per the accessibility floor. For type, drop the remote faces and name the local stack that will actually render (system sans for body, one system display weight for the short headings), then say how the "expressive hierarchy" survives without a webfont - e.g. weight, tracking, and the 30/36 step rather than a novelty face. If Limelight is genuinely load-bearing, say exactly how it ships inside a self-contained file, or drop it from §8 rather than leaving it as a claim.

---

**Bottom line.** The integration model is sound and the honesty floor is largely respected. What is missing is the application: two of four destinations, the optimistic-and-settle half of "reactive," the fixture rows that carry the hard permission and state cases, and a signature that does something C's inset does not. Fix those five and this can build.
